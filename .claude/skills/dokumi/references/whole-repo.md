# リポジトリ全体を対象にするとき

dokumi は、1 つの変更（PR にする前の diff）を検証するように作ってある。ユーザーが「リポジトリ全体に対して」「既存のコードを検証して」と頼んだときは、diff がないので、手順のいくつかを読み替える。頼まれていないのに全体へ広げない。全体の検証は、diff の検証の数倍から数十倍の時間とトークンを使う。

## 何が変わるか

| 項目 | diff を対象にするとき | 全体を対象にするとき |
|---|---|---|
| 要件 | 元の指示、issue | 仕様書、README、受け入れ条件。節ごとに番号を振る |
| 完了報告 | 生成エージェントの主張 | 文書がコードについて述べていること（「〜はすべて〜する」「〜に対応」）。文書の主張も裏を取る |
| 対象のファイル | ベースとの差分 | 追跡済みと未追跡の全ファイル（スクリプトに `--all`） |
| 「今回の変更」 | diff | 1 回目は対象の全部。再検証では修正の差分 |
| 影響範囲（段階 5） | diff の外で壊れるもの | 1 回目は対象外（外側がない）。再検証で、修正の差分に対して行う |
| mutator | `--since <mergeBase>` で変更行だけ | `--since` なしの全体実行。時間枠を見積もって決める |

## 1. 範囲を区切る

全部を 1 回で検証しようとしない。確認項目が増えるほど、どの要件を確かめていないかが見えにくくなり、1 回が終わる前に時間やトークンの上限に当たる。

- 仕様書の節か機能で区切り、1 回の検証の範囲を決める（例：「一覧と検索」「ドラッグと並び替え」「複数選択と取り消し」）。
- 区切り方と順番を、始める前にユーザーに示す。どこから始めるかはユーザーが決める。
- `.dokumi/requirements.md` には全部の要件を番号つきで書き、今回の範囲に入らない要件は「範囲外（次の回）」と書く。レポートの「要件ごとの確認」にも範囲外の行を残す。確かめていない要件が、確かめたように見えないようにするため。

範囲を区切っても、段階 1（機械ゲート）と段階 2（ごまかし検出）は全体に対して実行する。安く、全体で 1 回やれば足りる。

## 2. スクリプトの引数

```sh
node $SKILL/scripts/detect-project.mjs --all > .dokumi/project.json    # 全ファイルを対象として UI に触るかなどを判定
node $SKILL/scripts/scan-diff.mjs --all > .dokumi/scan.json            # 全ファイルの全行を検査
git diff HEAD -- . ':!.dokumi' > .dokumi/before.patch                  # 検証対象を変えていないことの確認用
```

`scan-diff.mjs --all` は、変更の前後を比べる検査（テストの削減、検査設定の変更、依存の追加）を行わない。既存のコード全体では、緩いアサーションや固定待ちが数十〜数百件出る。1 件ずつ読まず、種類ごとの件数を書き、blocker と、要件にかかわる場所のものだけを読む。

`--base` に最初のコミットを渡して全体の代わりにしない。最初のコミットから変わっていないファイルが対象から漏れる。

## 3. mutator の時間枠

全体実行は、SKILL.md の `--time-budget 300` では終わらない。実例：ソース 45 ファイル、ミュータント 2,760 件で、完走に約 1,700 秒かかった。1,500 秒では 46 件が未実行で残った。

```sh
npx mutator --time-budget <秒> --reporter agent > .dokumi/mutants.json 2> .dokumi/mutants.log
node $SKILL/scripts/triage-mutants.mjs .dokumi/mutants.json --mode <mode> > .dokumi/mutants-triage.json   # --base は渡さない
```

- 1 回目は時間枠を付けて流し、`counts` から 1 件あたりの時間を出して、完走に要る枠を見積もる。完走に 30 分を超えるなら、範囲の区切りに合わせて `--include 'src/<範囲>/**'` で対象を絞る。
- `Pending` が残った回の検出率は、前の回と比べない。分母が違う。
- 全体実行は 1 回の検証で 1 回にする。修正の確認は `--only <key>` か、直したファイルだけの `--include` で行う。
- 未検出はグループでも数百件になる。全部を指摘にしない。要件の振る舞いに対応する穴（「この振る舞いを壊しても全テストが通る」と言えるもの）を選んで指摘にし、残りはファイルごとの件数だけを書く。
- `--base` を渡さないので、振り分けの `where` は `unknown` になる。位置による重大度の引き下げは行われない。

## 4. 重大度の読み方

手順書の「変更した要素」「今回の変更で」は、次のように読む。

| 場面 | 「変更」に当たるもの | 理由 |
|---|---|---|
| 1 回目 | 今回の範囲に入るコードの全部 | 頼まれたのは既存のコードの検証で、「変更前からあった」を理由に外すと何も残らない |
| 再検証（修正の後） | 修正の差分 | 修正が持ち込んだ問題と、前からあった問題を分ける |
| 再検証で、前の回に行わなかった検査を足して見つかったもの | 1 回目と同じ（範囲に入るコードの全部） | 検査が遅れただけで、問題は前からあった。修正のせいではないが、範囲の中の問題である |

したがって 1 回目は、「変更前から存在した問題は note」の規則を使わない。要件に反すると実行で示せたものは blocker、axe の critical / serious は blocker、という表のとおりに付ける。原則 1（証明できた指摘だけが blocker）は変わらない。

blocker が多くなる。直す順番は、blocker の「実害」の行で決める。

## 5. 回数

「修正と再検証は最大 2 回」は、人の判断を挟まずに修正を繰り返す回数の上限で、全体が対象でも変わらない。全体の検証では、ESCALATE、人の判断、修正、再検証の周回が何度も起きる。人が答えるたびに数え直す。

同じコードに対してもう一度検証を頼まれたら（修正の差分が空）、前の回と同じ確認を繰り返さない。同じ確認は同じ結果を返すだけで、「2 回確かめたから安心」にはならない。`.dokumi/checks.md` で未確認だった要件、前の回に作らなかった状態、前の回に行わなかった検査（axe など）に範囲を広げ、何を足したかをレポートの冒頭に書く。

## 6. コストを先に伝える

始める前に、見込みをユーザーに伝える。実例（ソース 45 ファイル、テスト 650〜750 件）での 1 回分：

| 作業 | かかったもの |
|---|---|
| mutator の全体実行 | 25〜30 分 |
| 実ブラウザの確認（60〜70 項目のスクリプト 1 本） | 8〜10 分。作り直しを含めて 4〜5 回実行 |
| 独立レビュー（仕様との照合） | 約 29 万トークン |

独立レビューは省かない（試用で効果がいちばん大きかった段階である）。代わりに、範囲を区切って 1 回を小さくする。
