# 段階 4：mutator によるテストの質の実測

mutator は、コードを 1 か所ずつ小さく書き換え（ミュータント：`>=` を `>` に、戻り値を `""` に、呼び出しを削除）、それを実行するテストを走らせる。どのテストも落ちないミュータントは、カバレッジの数字に関係なくテストの穴である。

カバレッジは「実行された」ことしか示さない。AI が書いたテストは、コードを実行するだけで何もアサートしないことがよくある。mutator はそれを数字で示す。

## 使える条件

`detect-project.mjs` の `mutator.eligible` が判定する。

- Node.js 24 以上
- Vitest 5（または Vite+ の `vp test`）
- git リポジトリ

Jest（30 の ESM モードのみ、実験的）と Playwright ランナー（明示的な有効化が必要で、数分から数時間かかる）は、プロジェクトが既に `mutator.config.*` で設定している場合だけ使う。dokumi から新たに有効化はしない。PR 前の検証には重すぎるため。

Node.js が 24 未満でも、プロジェクトのテストが Node 24 で通るなら、一時的に Node 24 を用意して実行してよい（例：`npm i --no-save node@24` で `node_modules/.bin` に入る）。

## 導入

バージョンは `0.4.0` に固定する（0.x 系で、出力形式が変わり得るため）。

| 状況 | 対応 |
|---|---|
| `devDependencies` に既にある | そのまま `npx mutator` で使う。バージョンが違えば、そのバージョンの出力に従う。 |
| ない、npm のプロジェクト | `npm i --no-save @mizchi/mutator@0.4.0`。`package.json` を変えずに使える。 |
| ない、pnpm / yarn / bun のプロジェクト | 依存の追加は PR の差分を変えるので、勝手に入れない。[代替手順](#mutator-が使えないとき)に切り替え、レポートで導入を提案する。ユーザーが導入を許可済みなら `devDependencies` に追加する。 |

`npx -y @mizchi/mutator@0.4.0` のようにプロジェクト外から直接実行してはいけない。プロジェクトの Vitest と別の実体が読み込まれ、テストが通っているのに「ミュータントなしでテストが失敗（終了コード 4）」と誤って報告される（0.4.0 で確認）。必ずプロジェクトの `node_modules` に入れてから使う。

`.mutator/`（キャッシュとレポート）は、SKILL.md の段階 0 でローカルの除外設定に入れてある。プロジェクトが mutator を正式に導入するなら `.gitignore` に入れるべきだが、それは検証ではなくプロジェクト側の変更なので、レポートで提案するにとどめる。

## 実行

```sh
npx mutator --since <mergeBase> --include-test-changes --kill-matrix \
  --time-budget 300 --reporter agent > .dokumi/mutants.json 2> .dokumi/mutants.log
```

| フラグ | 理由 |
|---|---|
| `--since <mergeBase>` | diff 内のミュータントだけを実行して数える。既存コードの穴は今回の変更の責任ではない。 |
| `--include-test-changes` | 追加・変更・削除したテストが覆うミュータントも対象にする。テストを弱めた変更を拾うため。 |
| `--kill-matrix` | 各ミュータントに全テストを当てる。「何も検出しない新規テスト」を見つけるのに必要。通常の 1.1〜2.5 倍かかるが、diff 限定なら許容できる。 |
| `--time-budget 300` | 5 分で新しい実行を止める。残りは `Pending` になる。 |
| `--reporter agent` | 標準出力に JSON（ログは標準エラー）。 |

終了コード：

| コード | 意味 | 対応 |
|---|---|---|
| 0 | 完了 | 振り分けへ |
| 2 | プロジェクトの品質ゲートに不合格 | 未検出が残っていれば普通に起こる。JSON は完全なので振り分けへ |
| 4 | ミュータントなしでテストが失敗 | 段階 1 で通っているはずなので矛盾。[導入](#導入)の注意（プロジェクト外からの実行）を疑う |
| 1 | オプションや設定の誤り | ログを読んで直す |

## 結果の読み方

JSON の主な項目：

- `score`：検出率（0〜1 の小数。百分率ではない）。対象は[下の範囲](#対象に入る範囲)。
- `counts`：`Killed` / `Survived` / `NoCoverage` / `CompileError` / `Pending` などの件数。
- `gaps`：未検出ミュータント 1 件ごとの記録。`key`、`gap`（穴の種類）、`file`、`line`、`original` → `replacement`、囲む関数のソース（`scope.source`）、実行しているテスト（`coveredBy`）、`fix`（直し方の指針）。
- `warnings`：`skippedTest`（変更で追加・編集された skip）、`uncollectedTest`（変更したテストファイルがランナーに拾われていない）、`childProcessTest`。
- `findings`：`mutationGap`、`criticalGap`、`newTestNoKills`、`detectionRegression`、`testNotMeasured`。
- `comparison`：`unavailable` なら以前のスナップショットがなく、検出力の低下は判定されていない。

穴の種類は 3 つあり、それぞれ直し方が違う。

| `gap` | 意味 | 直し方 |
|---|---|---|
| `notReached` | どのテストもこのコードを実行していない | そこに到達するテストケースを足す（分岐、早期リターン、フォールバック） |
| `notInfected` | 実行はしているが、元とミュータントで値が変わる入力がない | 両者を区別する入力を足す。`>=` → `>` なら境界値そのもの |
| `notDetected` | 実行して値も変わるが、どのテストも落ちない | 変わる結果をアサートする。`toBeTruthy` を `toBe` に、部分一致を厳密な `toEqual` に |

`mutants: 0 in the diff` でスコアが 100% のときは、対象が何もなかっただけ（テストやドキュメントだけの変更、または `include` の範囲外）。実測できたとは書かない。既定の対象は `src/**` なので、ソースが別の場所にあるなら `--include` で指定する。

## 対象に入る範囲

mutator が実行して数えるのは、変更行のミュータントだけではない。

- **変更した関数の全体。** `--since` は関数単位で対象を決める。1 行だけ変えた関数でも、その関数の他の行のミュータントが入る。
- **変更したテストが実行する既存コード。** `--include-test-changes` を付けると、追加・変更したテストが通る既存の関数（共通コンポーネントやユーティリティ）も入る。

どちらも今回書き換えていない行を含む。`score` と `counts` はこの全体の値なので、そのまま「diff 内の検出率」と書かない。`triage-mutants.mjs` に `--base` を渡すと、未検出を変更行と突き合わせて 3 つに分ける。

| `where` | 意味 | 扱い |
|---|---|---|
| `changedLine` | ミュータントの位置が変更行に重なる | 線引きどおり |
| `changedFunction` | 変更した関数の中の、書き換えていない行 | 1 段階下げる（blocker → warning、warning → note） |
| `unchangedCode` | 変更したテストが実行するだけの既存コード | note（今回の変更の責任ではない） |

レポートに件数を書くときは、`byFile` の内訳から「変更行の未検出 N 件」と書き、全体の `score` には「変更した関数と、変更したテストが実行する既存コードを含む」と添える。

**`CompileError` は未実測。** 型検査を通らないミュータントは実行されず、`score` の分母にも入らない。変更の中心が型で縛られた値（文字列リテラル型の既定値、ユニオンの分岐など）だと、肝心の変更がミュータントにならない。`compileErrors` が多いとき、また変更行のミュータントが 0 件のときは、「mutator はこの変更を測っていない」とレポートに書き、段階 5 で直接確かめる。

## 重大度の線引き

```sh
node $SKILL/scripts/triage-mutants.mjs .dokumi/mutants.json --base <mergeBase> --mode <mode> > .dokumi/mutants-triage.json
```

終了コード 1 は「blocker あり」の意味で、スクリプトの失敗ではない（2 が失敗）。

出力の `groups` は、同じ関数・同じ種類の穴をまとめたもの。レポートではこの 1 行を 1 件の指摘として書く（「`App` のルーティングをどのテストも実行していない（9 件）」）。key は再確認用に添える。

| 重大度 | 対象 | 理由 |
|---|---|---|
| モードによる | `notReached`（変更コードをどのテストも実行していない） | `strict` では blocker。`standard` では warning（`needsEvidence`）で、他のレベルで確かめた証拠がなければ blocker に上げる（SKILL.md の段階 4） |
| blocker | `newTestNoKills`（新規テストが何も検出しない） | テストがあるように見せているだけ |
| blocker | `skippedTest` / `uncollectedTest` | そのテストは何も検証していない |
| blocker | `critical: true`（重要領域の未検出） | プロジェクトが「全部検出するか明示的に受け入れる」と決めた場所 |
| blocker | `detectionRegression` / `recheck: true` | 変更していないコードの検出力を落とした |
| warning | それ以外の `notDetected` / `notInfected` | 等価ミュータントを含み得るので、PR を止める根拠にはしない |

`notReached` を既定で blocker にしないのは、実行カバレッジを条件にすると、通すためだけのテストが書かれるから。コードを実行するだけで何も確かめないテストを足せば `notReached` は `notDetected`（warning）に変わるので、条件を満たすいちばん安い方法が中身のないテストになってしまう。配線や配置のコードは、単体テストより画面での確認が向いていることも多い。

全部を blocker にしないのは、等価ミュータント（どんな入力でも区別できないもの）が必ず混ざるため。スコアを 100% にすることを目標にすると、実装の細部をアサートする無意味なテストが増える。

重要領域は、プロジェクトの `mutator.config.*` の `critical`（glob）か、関数の直前の `// mutator-critical` コメントで指定されている。dokumi から勝手に指定を足したり外したりしない。認証、権限、金額計算の変更なのに指定がない場合は、レポートで指定を提案する。

`Pending` が残った場合（時間切れ）、未実測の件数をレポートに書く。実測できた範囲で判定し、残りは「未実測」とする。

## 修正と再確認

修正は生成エージェントの仕事で、検証（このスキル）の仕事ではない。FIX を返すときに次を渡す。

- blocker と warning の一覧（`mutants-triage.json` の `findings`）
- mutator 同梱の `mutation-test-loop` スキルがあればそれに従うこと（`npx mutator init-skill` で `.claude/skills/` に入る）

テストを書く側が守ること：

- **呼び出し側から観測できる振る舞いをアサートする。** 内部状態を覗く、テスト対象の関数をモックする、内部呼び出しの順序を固定する、のはしない。ミュータントは kill できるが、リファクタのたびに壊れるテストになる。
- **ミュータントを kill するためにテスト対象のコードを変えない。** 本物のバグを見つけた場合だけ別で、そのときは報告して止まる。
- テスト名はミュータントではなく振る舞いを表す。

再確認は該当ミュータントだけを数秒で行える。

```sh
npx mutator --only <key> --only <key> --reporter agent > .dokumi/mutants-recheck.json
```

`gaps` から消えていれば解消。多くは `counts.Killed` に入るが、到達していなかったミュータントは、到達させると `CompileError`（型検査を通らないので実行しない）に変わることがある。それも解消として扱う。まだ残るなら、同じ種類のテストを足すのではなく、入力かアサーションを見直す。

テストを足した後は key が変わることがある（`unknownKey` の警告が出る）。そのときは `--only` ではなく `--since` で全体を回し直す。修正案をコピー（worktree）の上で試すときも、その中で同じコマンドがそのまま使える。warning の未検出は 1 回だけ修正を試み、残ったものは PR 本文に載せる。

## 等価ミュータント

どんな入力でも元と区別できないミュータントがある。例：決して nullish にならない値への `?.`、誰も順序を読まない `.sort()`、呼び出し元が既に保証しているガード。

mutator には `mutator accept <key> --reason "..."` で `mutator.accepted.json` に記録する仕組みがある。**dokumi とその差し戻しを受けるエージェントは、これを実行しない。** エージェントが自分で受け入れられるなら、すべての穴を「等価です」で通せてしまう。

代わりに、等価だと考えるミュータントをレポートの「受け入れ提案」に載せる。

- key と場所（`file:line`、`original` → `replacement`）
- なぜどの入力でも観測できないのか（具体的に）
- 人が実行するコマンド

等価かどうか確信が持てないものは、提案せず「不明」として載せる。

`acceptance.killed`（受け入れ済みだが今は検出されている）と `acceptance.stale`（ミュータントがもう存在しない）は、`mutator.accepted.json` から消すべき項目としてレポートに載せる。

## 不要コードの候補

`gaps` のうち `simplify` が付いたものは、「コードを消してもどのテストも気づかない」ミュータント（文の削除、ブロックを空に、条件を常に true / false に、`?.` を `.` に）。`triage-mutants.mjs` の `simplifyCandidates` にまとまる。

これはテストの穴でもあり、不要なコードの候補でもある。mutator にはどちらか区別できない。1 件ずつ読んで決める。

- 要件にない防御や分岐で、消しても要件を満たす → 差分の最小性の指摘（warning）。消すことを提案する。
- 必要なコード → テストの穴として扱う。
- テストから見えない目的がある（高速パス、型のない呼び出し元への備え） → 受け入れ提案へ。

## mutator が使えないとき

実測の代わりに、手動の抜き取り検査を行う。原理は同じ。

1. 変更した関数・コンポーネントごとに、要件上もっとも大事な分岐か計算を 1〜2 か所選ぶ。
2. そこをコピーの上で壊す（条件を反転、境界を 1 ずらす、戻り値を固定値に、副作用の呼び出しを削除）。
3. 関係するテストを実行する。
4. 壊すのは作業ツリーではなくコピーの上で行う（`references/proving.md` の「壊して確かめる・直して確かめる」）。作業ツリーを直接編集すると、戻し忘れが検証対象を変えてしまう。
5. テストが落ちなければ、そのテストは壊れた振る舞いに気づかない。壊した内容、実行したコマンド、出力を証拠として記録する。

重大度は mutator のときと同じ線引き（どのテストも実行していない変更コードは blocker、落ちなかっただけなら warning）。

レポートには「mutator 未使用（理由）、手動の抜き取り N 件」と書く。抜き取りは網羅ではないので、「テストの質に問題なし」とは書かず、「抜き取った N 件はすべて検出された」と書く。
