# 段階 7：フロントエンド観点

diff と段階 6 の結果に照らして確認する。全項目を機械的に埋める表ではない。変更が触れた範囲に関係する項目を選び、関係しない項目は飛ばす。

blocker にするには証拠が要る（再現手順、コマンド出力、スクリーンショット）。読んで気づいただけの懸念は warning。既存コードの問題は対象外（今回の変更が持ち込んだもの、または悪化させたものだけ）。

## 状態の網羅

AI が書いた UI は、データが揃った正常系だけが作り込まれていることが多い。

- **ローディング**：取得中の表示があるか。レイアウトが取得後に大きく動かないか。
- **空**：0 件のときに空白や壊れた表ではなく、状況が分かる表示になるか。
- **エラー**：取得や送信の失敗がユーザーに伝わるか。再試行の手段があるか。握りつぶして何も起きない状態になっていないか。
- **部分的なデータ**：省略可能な項目が欠けたとき（`null`、`undefined`、空文字）に崩れないか。
- **極端な入力**：長い文字列、改行なしの長い単語、大量の件数、絵文字や多言語。
- **連打と競合**：送信ボタンの二重押し、応答が前後して返る場合（古い応答が新しい結果を上書きしないか）。
- **戻る・再読み込み**：URL に状態を持つべき場面で持っているか。再読み込みで入力が消えて困らないか。

## アクセシビリティ

- **キーボード**：すべての操作要素に `Tab` で到達でき、`Enter` / `Space` で動くか。`div` や `span` に `onClick` を付けただけの要素がないか。
- **フォーカス**：見えるか。モーダルやメニューを開いたときに中へ移り、閉じたときに元へ戻るか。
- **名前**：ボタン、リンク、入力欄に、読み上げられる名前があるか（アイコンだけのボタンの `aria-label`、`label` と入力欄の関連付け、画像の `alt`）。
- **意味のある要素**：見出し、リスト、ボタン、リンクを、見た目ではなく役割に合った要素で書いているか。`aria-*` で補う前に、ネイティブの要素で足りないか。
- **状態の通知**：エラーや非同期の結果が、視覚以外でも伝わるか（`aria-live`、`aria-invalid`、`aria-describedby`）。
- **色**：情報を色だけで伝えていないか。コントラストは十分か。
- **動き**：`prefers-reduced-motion` を尊重しているか（アニメーションを足した場合）。
- **文字の拡大**：ユーザーが文字を大きくしても読めるか（WCAG 1.4.4）。段階 6 でルートの文字サイズを 200% にして、今回足した・変えた文字が実際に大きくなるか、切れ・重なり・はみ出しが出ないかを測る（`references/browser-check.md` の「確かめる項目」）。大きくならないのは `px` で固定しているためで、`rem` / `em` にする提案を添える。入力欄の `font-size` が 16px 未満だと、iOS Safari はフォーカス時に画面を拡大する。見た目の印象ではなく、測った値とスクリーンショットで書く。

## レスポンシブ

- 375px 幅で横スクロールやはみ出しがないか。
- 固定幅や固定の高さを直書きしていないか。
- タッチ操作で押せる大きさか（目安 44px 四方）。ホバーでしか出ない情報や操作がないか。
- 表や長いコードなど、狭い幅で扱いが必要な要素の対処があるか。

## ブラウザ対応

AI は新しい CSS や Web API を、対応状況を確かめずに使うことがある。Chromium の Playwright だけで確かめると、ほかのブラウザで壊れても気づかない。

1. **今回の追加行で使い始めた機能を挙げる。** CSS のプロパティ、値、セレクタ、at-rule（`anchor-name`、`:has()`、`@starting-style` など）、Web API（`Popover`、`View Transitions` など）、HTML の属性。既存のコードで既に使っている機能は対象外。
2. **Baseline の状況を調べる。** [web-features](https://github.com/web-platform-dx/web-features) のデータを、axe と同じくプロジェクトの外に取得して読む（`npm install --prefix .dokumi/tools web-features`。`package.json` は変わらない）。`features[<id>].status.baseline` が `"high"` なら Widely available、`"low"` なら Newly available、`false` なら Baseline に入っていない。機能と id の対応は、各機能の `compat_features`（`css.properties.anchor-name` の形の文字列の配列）に、使った機能が含まれるものを探して引く。取得できなければ MDN の互換性表を読み、出どころをレポートに書く。
3. **Widely available でない機能には、代替手段があるか確かめる。** `@supports`、機能の有無の判定（`'popover' in HTMLElement.prototype` など）、ポリフィル。代替手段があれば「確認済み」に載せる。
4. **代替手段がなければ、プロジェクトが対応するブラウザを確かめる。** `package.json` の `browserslist`、`.browserslistrc`、README や設定に書かれた対応ブラウザ。
   - 決まっていて、その機能が使えないブラウザが含まれる → 段階 6 で、そのブラウザのエンジンで同じ確認項目を走らせる（`references/browser-check.md` の「確かめる項目」）。要件の操作が壊れるのを再現できたら blocker。再現しなければ（使えなくても見た目が少し変わるだけ、など）warning。
   - 決まっていない → Baseline の状況を証拠に warning。対応ブラウザを決めておく提案を添える。

Baseline の状況だけで blocker にしない。対応するブラウザで実際に壊れると示せたときだけ止める。

## フレームワーク特有のミス

プロジェクトのフレームワーク（`project.json` の `framework`）に該当するものを見る。

**React**
- effect の依存配列の漏れや過剰。lint を無効化して通していないか（段階 2 の `lint-suppress`）。
- effect が不要な場面で使われていないか（props や state から計算できる値を state に複製して effect で同期する、など）。
- リストの `key` に配列のインデックスや乱数を使っていないか（並び替え、追加、削除があるリスト）。
- effect のクリーンアップ（購読、タイマー、リクエストの中止）。
- state の直接変更。
- レンダーごとに新しいオブジェクトや関数を作り、メモ化した子や effect を毎回動かしていないか（実際に問題になる場合のみ）。
- React Compiler を使うプロジェクトで、不要な手動メモ化を足していないか。

**Next.js などサーバーとクライアントの境界があるもの**
- `"use client"` の範囲が必要以上に広くないか。サーバー専用の値（秘密情報、サーバー専用モジュール）がクライアントに渡っていないか。
- サーバーとクライアントで出力が変わる値（日時、乱数、`window` の参照）によるハイドレーションの不一致。
- データ取得のキャッシュと再検証の設定が要件に合っているか。

**Vue / Svelte など**
- リアクティビティが切れる書き方（分割代入、リアクティブでない値への代入）。
- watcher や購読の後始末。

## 型の規律

- **境界でパースする**：API レスポンス、フォーム入力、URL パラメータ、localStorage など外部から来るデータを、型アサーション（`as`）で通さず、検証して型を付けているか（プロジェクトが使うスキーマライブラリに従う）。
- **不正な状態を表せない型**：`isLoading`、`error`、`data` を別々の真偽値や省略可能な項目で持たず、判別可能なユニオンにできないか。あり得ない組み合わせを型が許していないか。
- **分岐の網羅**：ユニオンの分岐に、種類が増えたときコンパイルエラーになる仕掛け（`never` での網羅チェック）があるか。
- **型の出どころ**：スキーマや API 定義から導ける型を、手書きで複製していないか。
- `any`、`as`、非 null アサーション（`!`）の追加は、段階 2 の結果と合わせて 1 件ずつ理由を確かめる。

## デザインの一貫性

- 色、余白、文字サイズ、角丸、影を、プロジェクトのデザイントークンやテーマを使わず直書きしていないか。
- 既存の共通コンポーネント（ボタン、入力欄、モーダルなど）があるのに、似たものを新しく作っていないか。
- **似た要素が同じように振る舞うか**：今回足したボタン、リンク、入力欄などを、画面にある同じ役割の既存の要素と比べる。段階 6 で両方にホバー、フォーカス、無効状態を作り、計算後のスタイル（色、枠線、フォーカスリング、カーソル）を並べるか、スクリーンショットを並べる。違いがあれば、両方の値かスクリーンショットを添えて warning。比べる相手の既存の要素が画面にないときは飛ばす。
- ダークモードやテーマ切り替えがあるプロジェクトで、両方で読めるか。
- 文言を直書きしていないか（国際化の仕組みがあるプロジェクトの場合）。

## 差分の最小性

AI は頼まれた以上のものを書きがちで、それがレビューの負担と不具合の入口になる。

- 要件に対して変更が大きすぎないか。関係のないファイルの整形や書き換えが混ざっていないか（段階 3 の「要件にない変更」と合わせる）。
- 呼び出し元が 1 か所だけのラッパー、使われていない引数やオプション、将来のための抽象化。
- 既にあるユーティリティやフックの再実装。
- 起こり得ない状態への防御、不要な後方互換の層。
- 消しても何も変わらないコード（段階 4 の `simplifyCandidates`）。
- コードを言い直しているだけのコメント、変更の経緯を語るコメント（それはコミットメッセージに書く）。

該当があれば、消す・既存のものを使うことを warning として提案する。動作に影響しない限り blocker にはしない。

## バンドルとパフォーマンス

- 追加した依存（段階 2 の `dependency-added`）の大きさ。同じことが既存の依存や標準 API でできないか。
- ライブラリ全体を import していないか（必要な部分だけを import できる場合）。
- 初期表示に要らない重いコンポーネントを、遅延読み込みにできないか。
- 画像の寸法指定、遅延読み込み、適切な形式。
- プロジェクトにバンドルサイズの計測手段（サイズ上限の検査、アナライザー）があれば、ベースと比べて増分を数字で示す。なければ、ビルド出力のサイズをベースと比べる。

数字なしに「重くなる」と書かない。測れないなら warning として「未計測」と添える。

## セキュリティ

- `dangerouslySetInnerHTML`、`v-html`、`innerHTML` に、無害化していない外部由来の値を渡していないか。
- ユーザー入力から組み立てた URL を `href` や遷移先に使っていないか（`javascript:` スキーム、オープンリダイレクト）。
- 秘密情報（API キー、トークン）をクライアントのコードや公開される環境変数に入れていないか。
- `target="_blank"` の外部リンク、`postMessage` の送信元の検証。

外部由来の値が無害化なしで HTML として描画されることを実際に示せたら blocker。
