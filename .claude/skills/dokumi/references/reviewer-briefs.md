# 別エージェントへの依頼文

段階 3 と 4 で使う。生成時の文脈を持たないエージェントに、下の依頼文と指定の入力だけを渡す。

渡さないもの：生成時の会話、実装方針の説明、「ここは問題ないはず」といった自分の見立て。渡すと、相手はその見立てを確認して返してくる。

依頼文の `<...>` を実際の値に置き換える。作業ディレクトリは対象リポジトリにする。相手の再現用ファイルは `.dokumi/review/` に置かせる（作業ツリーを汚さないため）。

## 要件適合

```
フロントエンドの変更が要件を満たしているかを検証してください。あなたはこの変更を書いていません。
書いた側の説明は信用せず、要件と実際のコードだけから判断してください。

入力:
- 要件: .dokumi/requirements.md
- 変更: `git diff <mergeBase>` と `git ls-files --others --exclude-standard`（未追跡の新規ファイル）
- 書いた側の完了報告: .dokumi/claims.md

調べること:
1. 要件の各項目について、対応する実装があり、実際に動くか。
2. 要件にない変更が含まれていないか（頼まれていないリファクタ、無関係なファイルの変更、
   仕様の勝手な拡張）。
3. 完了報告の各主張が、実際の差分や実行結果と一致するか（「テストを追加した」→
   そのテストは存在し、実行され、通るか。「対応した」→ 該当コードがあるか）。
4. 使っている import、API、props、設定キー、CLI フラグ、パッケージが実在するか。
   node_modules の実際のバージョンの型定義やソースで確かめる。

指摘のルール:
- 実行して確かめたものだけを報告する。失敗するテスト、再現スクリプト、誤った挙動を示す
  コマンド出力のいずれかを付ける。再現用のファイルは .dokumi/review/ に置き、
  既存のファイルは変更しない。テストの実行方法は、スキルの references/proving.md の
  「再現テストを書いて実行する」に従う（<proving.md の絶対パス>）。
- 各指摘に、題名、実行したコマンド、出力された内容、要件が求める内容を書く。
- 実行していないものは「未検証の懸念」として分けて書く。
- スタイル、命名、構造の好み、将来の変更がなければ問題にならないリスクは書かない。
- 要件の文言が複数の解釈を許す箇所は、どちらの解釈で実装されているかと、
  もう一方の解釈を「要確認」として書く。
- 問題が見つからなければ「検証済みの指摘なし」と書く。それは正当な結果です。

返す形式:
## 要件ごとの判定
| 要件 | 判定（満たす / 満たさない / 確認できず） | 根拠（file:line または実行したコマンド） |
## 検証済みの指摘
## 要件にない変更
## 完了報告との食い違い
## 未検証の懸念
## 要確認（解釈が割れる箇所）
```

## テストの質

mutator は「振る舞いを壊したら落ちるか」を測る。この依頼は、mutator では測れない残り半分、
「内部だけ変えても通り続けるか」を判定させる。

```
この変更で追加・変更されたテストが、実装ではなく振る舞いを検証しているかを判定してください。
あなたはこのテストを書いていません。

入力:
- 変更: `git diff <mergeBase>` と未追跡の新規ファイル
- 要件: .dokumi/requirements.md

テストは「コードの利用者が観測できること」についての主張です。観測できるものは、戻り値、
エラー、読み戻せる状態、画面に表示される内容、外部への呼び出し（API リクエストなど）。
プライベートな関数、内部の呼び出し順、中間データ、コンポーネントの内部 state は実装です。

追加・変更されたテストごとに、2 つの編集を想像して判定してください。
A. 振る舞いを壊す（誤った値、抜けた・重複した副作用）。テストが通り続けるなら、何も証明していない。
   典型: 緩いアサーション、テスト対象のコードで計算した期待値、テスト自身が作ったデータへのアサート、
   モックの戻り値をそのままアサート。
B. 観測できる結果を保ったまま内部を変える（関数の分割、state の持ち方の変更、別のフックへの
   置き換え）。テストが落ちるなら、実装に張り付いている。
   典型: 内部関数のモックと呼び出し回数のアサート、実装の詳細を写したスナップショット、
   クラス名や DOM 構造へのアサート、テスト用の id ではなく実装都合のセレクタ。

疑わしいテストは、実際に編集して実行して確かめてください。
- A の確認: テスト対象のコードを壊してテストを実行する。
- B の確認: 振る舞いを保つ小さなリファクタをしてテストを実行する。
編集は作業ツリーではなく、.dokumi/review/ の下に作ったソースのコピーの上で行ってください
（手順は <proving.md の絶対パス> の「壊して確かめる・直して確かめる」）。既存のファイルは変更しないでください。

フロントエンド特有の観点:
- コンポーネントのテストは、ユーザーが見て操作するもの（ロール、ラベル、表示テキスト）を
  通じて書かれているか。
- 非同期の表示（ローディング、エラー、空）がそれぞれテストされているか。
- 期待値は要件から導かれているか（実装の出力を貼り付けただけでないか）。
- 「起こらない」ことのテストには、起こる場合のテストが対になっているか。

指摘のルール:
- 実際に編集して実行したものだけを「検証済み」とし、編集内容、コマンド、出力を付ける。
- 実行していない見立ては「未検証の懸念」として分ける。
- 問題がなければ「検証済みの指摘なし」と書く。

返す形式:
## テストごとの判定
| テスト | A: 壊したら落ちるか | B: 内部変更で通り続けるか | 根拠 |
## 検証済みの指摘
## 未検証の懸念
```

## 返ってきた指摘の扱い

返答をそのままレポートに転記しない。

1. 「検証済みの指摘」の各コマンドを自分で再実行する。
2. 出力が失敗を示し、かつ要件に反するものだけを残す。
3. 根本原因が同じ指摘はまとめる。
4. 再現しなかったものは捨て、件数と理由をレポートの「捨てた指摘」に書く。
5. 「未検証の懸念」は、安く確かめられるなら自分で確かめる。確かめられなければ warning として載せる。
6. 「要確認」が 1 件でもあり、どちらの解釈かで実装が変わるなら、判定は ESCALATE。直し方が明確な blocker が他にあっても同じ（SKILL.md の段階 8）。

相手が残した `.dokumi/review/` の再現ファイルは証拠として残す。相手が既存ファイルを変更していないか、`.dokumi/before.patch` との比較で確かめる（`references/proving.md`）。

## 別エージェントを起動できないとき

同じ依頼文を自分への指示として使う。`.dokumi/requirements.md`、`.dokumi/claims.md`、diff だけを読み直し、生成時の経緯は判断材料にしない。編集して確かめる部分は、作業ツリーではなくコピーの上で行う。レポートの該当段階に「独立レビューなし」と書く。自分で書いた変更を自分で検証している場合は、そのこともレポートに書く（見落としの可能性を読み手が割り引けるように）。
