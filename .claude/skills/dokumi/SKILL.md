# dokumi（毒味）

AI エージェントが書いたフロントエンドの変更を、PR にする前に検証する。

生成したエージェントは自分の実装に甘い。テストが通ること、コンパイルが通ること、「対応しました」という報告は、どれも変更が正しいことの証拠にならない。このスキルは**実物を動かして得た証拠だけ**を信じ、証拠のない主張を PR に持ち込ませない。

## 原則

各段階で迷ったらここに戻る。

1. **証明できた指摘だけが PR を止める。** blocker にできるのは、コマンドとその出力で示せる指摘だけ。読んで怪しいと思っただけのものは warning にとどめる。レビューが「それらしい懸念の列挙」になると、差し戻しが終わらず、人も読まなくなる。
2. **実物で確かめる。** 機能を動かし、実際の値を読み、実際の差分を見る。「コンパイルが通る」、自己申告、キャッシュされた出力は証拠にしない。確認が失敗したら、システムより先に確認方法を疑う。
3. **評価者を生成者から切り離す。** 要件適合とテストの質の判定は、生成時の文脈を持たない別エージェントに任せる。自分で書いたコードは、書いた意図どおりに読めてしまう。
4. **指摘なしは正当な結果。** 何か見つけることが目的ではない。スタイル、命名、好みの問題は対象外。
5. **検証中は直さない。** 検証と修正を混ぜると、何を検証したのかが分からなくなる。全段階を終えて判定を出してから、修正に戻る。壊して確かめる、修正案を試す、といった実験は、作業ツリーではなくコピーの上で行う（`references/proving.md`）。

## モード

何を PR の条件にするかは、コードの性質と、人がどこで関わりたいかで変わる。次の 2 つを切り替えられる。指定がなければ既定値を使う。

| 設定 | 値 | 意味 |
|---|---|---|
| `mode` | `standard`（既定） | 変更の振る舞いを、**どのレベルでも確かめた証拠がない**ときに止める。自動テストがなくても、実ブラウザ検証などで確かめてあれば warning にとどめる |
| | `strict` | 変更したコードをどのテストも実行していなければ止める（変更行の実行カバレッジ 100% を求めるのと同じ）。ライブラリや、画面で確かめにくいロジック中心のコード向け |
| `onWarning` | `report`（既定） | warning は PR 本文に載せ、レビューで人が判断する |
| | `ask` | **判断が要る warning** が 1 件でもあれば、PR を作る前に人に確認する（判定は ESCALATE）。人がその場にいる対話的な作業向け。無人の実行では止まったままになるので使わない |

指定の出どころは、優先順に次のとおり。

1. 呼び出し時のユーザーの指示（「strict で検証して」「warning は確認して」）
2. プロジェクト直下の `dokumi.config.json`（例：`{ "mode": "strict", "onWarning": "report" }`）
3. 既定値

使ったモードはレポートの冒頭に書く。モードを自分の判断で緩めない（blocker を消すために `strict` を `standard` に変える、は修正ではない）。

`standard` を既定にしているのは、テストのレベルを選ぶ余地を残すため。配線や配置のコードは単体テストより画面での確認が向いている。実行カバレッジを条件にすると、通すためだけの中身のないテストが増える。

**どこまでテストを求めるかは、まずプロジェクト自身の基準に従う。** dokumi が独自の線を引くのは、プロジェクトが何も決めていない部分だけ。

| プロジェクトが決めていること | dokumi の扱い |
|---|---|
| テストフレームワークのカバレッジのしきい値（Vitest の `coverage.thresholds`、Jest の `coverageThreshold` など） | 段階 1 でカバレッジつきのテストを実行し、しきい値を割ったら blocker。プロジェクトの条件そのものなので、モードによらない |
| mutator の重要領域（`critical`）やしきい値（`thresholds.break`） | 段階 4 で、未検出があれば blocker。モードによらない |
| 上のどちらもない | `mode` に従う（`standard` なら「どのレベルでも確かめた証拠がない」ときだけ止める） |

しきい値を満たしていても、今回の変更がテストされているとは限らない（全体で 80% を保ったまま、新しいコードが丸ごと未テストということはあり得る）。だからしきい値に合格していても、段階 4 の「どのテストも実行していない変更コード」の扱いは省かない。

しきい値や重要領域の設定を今回の変更で緩めていれば、段階 2 が「検査の設定ファイルを変更」として検出する。基準を下げて通すのは修正ではないので、差分を読んで、下げていれば blocker にする（要件がそれを求めている場合を除く）。

カバレッジの設定の変更は、基準を下げたのか、計測の対象を整えたのかを差分で区別する。

| 変更 | 扱い |
|---|---|
| しきい値の数値を下げる、製品コードを計測の対象から外す | 基準を下げている。blocker |
| テスト用の共通部品やフィクスチャを計測の対象から外す | 計測を製品コードに合わせている。外したパターンに当たるファイルを列挙し、製品コードが 1 つも含まれないことを示せば「確認済み」にしてよい |

### 判断が要る warning

warning の全部を人に確認させると、確認が形だけになる。人の判断が要るのは次のものに限り、レポートでは他の warning と分けて「判断してほしいこと」に載せる（`report.json` では `needsDecision: true`）。

- **自動テストなしの変更**：振る舞いは検証時に確かめたが、それを守る自動テストがない
- **等価ミュータントの受け入れ提案**
- **要件にない変更**：頼まれていない変更が含まれるが、害は確認されていない
- **要件の中心にかかわる未確認**：確かめられなかった項目が残っている

それ以外の warning（`any` の追加、緩いアサーション、軽微な崩れなど）は情報として載せる。

## 入力

始める前に次の 3 つを揃える。

| 入力 | 取り方 |
|---|---|
| **要件** | 元の指示、issue、仕様。会話にあればそれを使う。なければユーザーに尋ねる（要件なしでは適合を判定できない）。 |
| **diff** | ベースブランチとの merge-base から作業ツリーまで。未コミットと未追跡のファイルも含む。 |
| **完了報告** | 生成エージェントが「やった」と主張している内容。自分が生成者なら、検証前に箇条書きで書き出す。 |

要件と完了報告は `.dokumi/requirements.md` と `.dokumi/claims.md` に書き出す。別エージェントに渡すためと、後で突き合わせるため。

要件は 1 項目ずつ番号を振って書き出す（`- R1: 検索欄が空なら検索ボタンを押せない`）。仕様書が要件なら、節や受け入れ条件ごとに 1 項目にし、1 つの節に別々に壊れ得る振る舞いが複数あれば分ける。この番号で、どの要件を何で確かめたかを最後に突き合わせる（段階 8 の「要件ごとの確認」）。PASS が意味するのは「確かめた項目は通った」ことだけなので、確認項目が 1 つもない要件を、番号で機械的に洗い出せるようにしておく。

diff ではなくリポジトリ全体（既存のコード）を対象にするよう頼まれたときは、先に `references/whole-repo.md` を読む。対象の区切り方、スクリプトの引数、時間枠、重大度の読み方が変わる。

要件に「実データで確かめる」条件があるとき（「実データ 51 点で上位が入れ替わる」など）は、そのデータの場所も入力に含める。リポジトリにも会話にもなければ、始める前にユーザーに尋ねる。受け取ったデータは `.dokumi/` の下か検証対象の外に置き、コミットしない。手に入らなければ、その条件は「未確認」として残す。

要件や完了報告が作業ツリーにファイルとして置かれている場合（未追跡の `REQUIREMENTS.md` など）、それは検証の入力であって変更の一部ではない。「要件にない変更」には数えず、PR に混ざらないよう note で知らせる。

`.dokumi/` は作業用ディレクトリ。検証の作業ファイルで PR の差分を変えないよう、`.gitignore` ではなくリポジトリのローカル除外設定に入れる（下の段階 0）。

## 流れ

安く確実な検査から順に進める。段階 1 が落ちたら、そこで打ち切って FIX を出す（壊れたコードの上で後段を回しても結果を信用できない）。それ以外の段階は blocker が出ても最後まで進め、指摘をまとめて返す。

```
0. 準備            プロジェクト構成とベースを特定
1. 機械ゲート       型・lint・テスト・ビルド            ← 落ちたら打ち切り
2. ごまかし検出      追加行の機械検査
3. 要件適合         別エージェントが要件と diff を照合
4. テストの質       mutator の実測 + 実装への張り付き判定
5. 影響範囲         安全の根拠を 1 つ特定して実行で証明
6. 実ブラウザ検証    UI に触る diff のときだけ
7. フロントエンド観点 状態・a11y・レスポンシブ・型など
8. 判定とレポート    PASS / FIX / ESCALATE
```

以下、`$SKILL` はこのスキルのディレクトリを指す。

### 0. 準備

```sh
mkdir -p .dokumi
# 作業ファイルをローカルでだけ無視する（コミットされないので PR の差分に影響しない）
exclude=$(git rev-parse --git-path info/exclude); mkdir -p "$(dirname "$exclude")"
for d in .dokumi/ .mutator/; do grep -qxF "$d" "$exclude" 2>/dev/null || echo "$d" >> "$exclude"; done

node $SKILL/scripts/detect-project.mjs > .dokumi/project.json
git diff <mergeBase> -- . ':!.dokumi' > .dokumi/before.patch   # 最後に、検証対象を変えていないことの確認に使う
```

依存が入っていなければ（`node_modules` がない）、先にプロジェクトのロックファイルどおりに入れる（`npm ci` など）。`package.json` やロックファイルが変わる入れ方はしない。

`git rev-parse --git-path info/exclude` は、git worktree の中では本体リポジトリの `.git/info/exclude` を指す（除外設定は worktree 間で共有される）。書き込むのは作業ディレクトリの 2 行だけで、コミットにも他の worktree の差分にも影響しないので、そのまま実行してよい。

出力から、使うコマンド（`commands`）、ベース（`base.mergeBase`）、mutator が使えるか（`mutator.eligible`）、UI に触る diff か（`diff.touchesUi`）を読む。`engines.satisfied` が false なら、実行中の Node がプロジェクトの指定と違う。合わせられるなら合わせ、合わせられなければレポートの「検証の副作用」に書く。モノレポなら `--root` で対象パッケージを指定する。ベースが特定できなければ `--base <ref>` を渡す。

`commands` が `null` の項目は、その検査がプロジェクトに存在しないということ。勝手に検査を追加せず、レポートに「未設定のため未実施」と書く。

`interference` の `testFilesUnderSkills` か `testFilesUnderWork` にファイルがあれば、スキルの試験用ファイル（`evals/`）や前の回の作業ファイル（`.dokumi/review/` の再現テスト）が、プロジェクトのテストや lint に混ざり得る。段階 1 の「作業ファイルが検査に混ざったとき」のとおりに扱う。`testFilesUnderSkills` に `dokumi/evals/` があるときは、動作に不要なので消してよいことを、レポートの「検証の副作用」でユーザーに伝える（自分では消さない）。

### 1. 機械ゲート

`commands` の `typecheck`、`lint`、`test`、`build` を順に実行する。出力は `.dokumi/gate-<名前>.log` に保存する。

`coverage.thresholdsConfigured` が true なら、`coverage.command` も実行する（`test` と同じコマンドでカバレッジまで測るプロジェクトなら 1 回でよい）。しきい値は、カバレッジを測る実行でしか検査されないことが多い。普段の `npm test` が通っていても、それだけでは基準を満たした証拠にならない。

- 1 つでも失敗したら blocker。失敗した出力の該当部分を証拠として記録し、後段に進まず段階 8 へ。
- ベースブランチの時点で既に失敗していた検査は、今回の変更の責任ではない。ベースの worktree で同じ検査を走らせて確かめ（`references/proving.md` の「ベースと比べる」）、既存の失敗なら warning として区別する。`git stash` は未コミットの変更を退避してしまうので使わない。
- テストが 1 件も実行されていない（0 tests）のは成功ではない。blocker として扱う。
- カバレッジのしきい値を割ったら blocker。どの指標（行、分岐、関数）がいくつ足りないかと、今回の変更で下がったのか元から割っていたのか（ベースの worktree で同じコマンドを実行して比べる）を記録する。元から割っていたなら warning。
- しきい値は設定されているのに実行手段がない（`coverage.command` が null）ときは、依存を足さず、「カバレッジのしきい値は未検査」と報告する。
- **作業ファイルが検査に混ざったとき。** 失敗したファイルがすべて `.dokumi/` か `.claude/skills/` の中なら、変更の問題ではない。blocker にせず、そのパスを対象から外して同じ検査をやり直し、その結果で判定する。Vitest は `--exclude '.dokumi/**' --exclude '.claude/**'`、ESLint は `--ignore-pattern`、対象を引数で取る lint（Biome など）は検査するパスを明示する。プロジェクトの設定ファイルは変えない。外して実行したことと、設定で除外する提案を、レポートの「検証の副作用」に書く。

### 2. ごまかし検出

```sh
node $SKILL/scripts/scan-diff.mjs --base <mergeBase> > .dokumi/scan.json
```

追加行だけを対象に、`.only` / `.skip`、`@ts-ignore`、`any`、lint の無効化、握りつぶした例外、スタブ、デバッグ出力、スナップショットの更新、検査設定の変更、依存の追加、テストの削減を検出する。

終了コード 1 は「blocker あり」の意味で、スクリプトの失敗ではない（2 が実行失敗）。`triage-mutants.mjs` も同じ。

スクリプトの `blocker` はそのまま blocker にする（文字列として存在することが証拠）。`warning` と `note` は 1 件ずつ該当箇所を読み、次のどれかに決める。

- **正当**：理由がコードやコミットから読み取れる。レポートの「確認済み」に理由つきで載せる。
- **warning のまま**：判断がつかない、または理由が書かれていない。
- **blocker に格上げ**：ごまかしだと実行で示せた場合（例：握りつぶした例外のせいでエラー表示が出ないことを再現した）。

機械検査では拾えない、**症状だけを隠す修正**もここで見る。バグ修正の diff では、追加されたガード、リトライ、既定値へのフォールバック、値の丸め込みが「あってはならない状態」を隠していないかを確かめる。その状態が正当に起こり得るなら、そこで扱うのは正しい。起こるはずがないなら、それを生んだ場所が直っていない。

### 3. 要件適合

別エージェントに任せる。依頼文は `references/reviewer-briefs.md` の「要件適合」をそのまま使い、要件、diff、完了報告だけを渡す。生成時の会話や自分の解釈は渡さない。

サブエージェントを起動できない環境では、自分で行う。その場合は `.dokumi/requirements.md` と diff だけを読み直して判定し、レポートに「独立レビューなし」と明記する。

返ってきた指摘は鵜呑みにしない。各指摘のコマンドを自分で再実行し、出力が失敗を示していて、かつ要件に反するものだけを残す。再現しない指摘は捨て、捨てた件数と理由をレポートに書く。

残った指摘の重大度は次のとおり。

| 指摘 | 重大度 |
|---|---|
| 要件が明示している振る舞いや数値に反し、再現できた | blocker。今のデータで起きているかどうかは重大度を変えず、レポートの「実害」の行で区別する（`references/report-format.md`） |
| 要件の文言が複数の解釈を許し、実装はその一方に従っている | warning（判断が要る）。どちらの解釈かで実装が変わるなら、判定は ESCALATE（段階 8） |
| 要件にない変更で、害は確認されていない | warning（判断が要る） |
| 再現していない懸念 | warning |

要件に「実データで確かめる」「N 件以上入れ替わる」のような条件があり、測る条件（日付、入力、設定の組み合わせ）が書かれていないときは、その機能の結果を左右する軸を 2〜3 本選び、それぞれ複数の値で測る。1 つの条件だけで「満たす」と書かない。選んだ条件はレポートに書く（読み手が別の条件で測り直せるように）。

### 4. テストの質

**`mutator.eligible` が true の場合**、`references/mutation.md` に従って mutator を実行し、結果を振り分ける。

```sh
# 1 回目：変更行だけを測る。判定の土台はこの結果
npx mutator --since <mergeBase> --time-budget 300 --reporter agent \
  > .dokumi/mutants.json 2> .dokumi/mutants.log
node $SKILL/scripts/triage-mutants.mjs .dokumi/mutants.json --base <mergeBase> --mode <mode> > .dokumi/mutants-triage.json

# 2 回目：範囲を広げる。1 回目に Pending が残らなかったときだけ
npx mutator --since <mergeBase> --include-test-changes --kill-matrix --time-budget 300 --reporter agent \
  > .dokumi/mutants-wide.json 2> .dokumi/mutants-wide.log
node $SKILL/scripts/triage-mutants.mjs .dokumi/mutants-wide.json --base <mergeBase> --mode <mode> > .dokumi/mutants-wide-triage.json
```

2 回に分けるのは、広げた範囲が時間枠に収まらないことがあるため。変更したテストが画面全体を描画していると、対象は既存コードのほぼ全部に広がる（実例：変更行 48 件に対して 1386 件。5 分で 8 割が未実行のまま打ち切られ、変更行の一部も測られなかった）。先に変更行を測っておけば、2 回目が打ち切られても判定の土台は残る。2 回目からは、1 回目では出ない種類の指摘（何も検出しない新規テスト、既存の検出力の低下、今回書き換えていない行の穴）だけを足す。2 回目に `Pending` が残ったら、それらは「未判定」としてレポートに書き、時間枠を延ばして粘らない（`references/mutation.md` の「実行」）。

`mutator.installed` が false なら、先に `references/mutation.md` の「導入」に従って入れる（npm のプロジェクトなら `--no-save` で入り、`package.json` は変わらない）。`--mode` は振り分けスクリプトへの引数で、mutator 本体には渡さない。振り分けの線引きはスクリプトに固定してある（何も検出しない新規テスト、重要領域の未検出、skip されたテスト、既存の検出力の低下が blocker。それ以外の未検出は warning。今回書き換えていない行の穴は 1 段階下げるか note）。

どのテストも実行していない変更コードは、`strict` なら blocker。`standard` なら `needsEvidence: true` の warning で出てくるので、段階 6 まで終えてから 1 件ずつ決める。

- その変更の振る舞いを、実ブラウザ検証や再現テストで実際に確かめた証拠がある → warning のまま、「自動テストなしの変更」として判断が要る warning に入れる。証拠（どの確認項目か）を添える。
- 証拠がない（UI に触らない変更で段階 6 を飛ばした、画面に到達できなかった、確かめる項目に入れていなかった） → blocker に上げる。まず確かめる手段を足せないか検討し、足せたなら上の扱いにする。

「画面が表示された」は、その変更の振る舞いを確かめた証拠にならない。足した分岐や配置が実際に効いていることを示す確認項目が要る。レポートには `groups` の 1 行を 1 件の指摘として書く。同じ関数の同じ種類の穴は、たいてい 1 つのテスト不足が原因だからである。等価ミュータントの受け入れ（`mutator accept`）は実行しない。理由つきの提案としてレポートに載せ、人が決める。人が key を指定して実行を頼んだ場合だけ、代わりに実行してよい（`references/mutation.md` の「等価ミュータント」）。

**false の場合**は `references/mutation.md` の「mutator が使えないとき」の手順で、変更した関数ごとに手動でミュータントを 1〜2 個入れて確かめる。レポートには実測ではなく抜き取り検査であることを書く。

どちらの場合も、mutator では測れないもう半分を別エージェントに判定させる（`references/reviewer-briefs.md` の「テストの質」）。振る舞いを保ったまま内部だけ変えたときに落ちるテスト、つまり実装に張り付いたテストの検出。サブエージェントを起動できない環境では、段階 3 と同じく自分で行い（コピーの上で振る舞いを保つ書き換えを 1 つ入れてテストを走らせる）、「独立レビューなし」と書く。

mutator の数字を「変更は実測済み」の意味で読まない。型検査を通らないミュータント（`mutants.json` の `counts.CompileError`、振り分け結果の `compileErrors`）は実行されないので、変更の中心が型で縛られた値（文字列リテラル型の既定値など）だと、そこは測られていない。その場合は段階 5 で直接確かめる。

### 5. 影響範囲

diff の外で壊れるものを探す。呼び出し元の列挙は目的ではない（grep で出る）。grep で出ない壊れ方を探す。

1. **変更を読む。** 追加・変更・削除されたシンボルと、diff が明示していない振る舞いの変化。
2. **安全の根拠を 1 つ特定する。** 危なく見える変更の多くは、1 つの事実のおかげで安全になっている（例：「この props は省略時に従来と同じ値になる」）。その事実を文にする。
3. **grep が届かない場所を見る。** フロントエンドでは次が典型。
   - 共有コンポーネントや共通フック、デザイントークン、グローバル CSS の変更が及ぶ他の画面
   - API レスポンスの形、localStorage や URL クエリの形式、保存済みデータとの互換
   - 実行のタイミング（アンマウント後の更新、Suspense、サーバーとクライアントの境界、ハイドレーション）
   - 使っているライブラリの実際のバージョンでの挙動（`node_modules` のソースを読む）
   - ルーティング、機能フラグ、環境変数の有無による分岐
4. **その事実を実行で証明する。** 実際のコードを呼ぶスクリプトかテストを書いて走らせ、出力を貼る。証明できなければ「未証明」と書く。壊れていると考えるなら、同じテストが作業ツリーで失敗しベースで通ることを示す（`references/proving.md`）。

確かさは次の段階で表し、どこまで到達したかをレポートに書く。

| 段階 | 状態 |
|---|---|
| 1 | そう述べただけ（これだけでは無価値） |
| 2 | 該当行を示した |
| 3 | 失敗の経路を追って、到達しないことを示した |
| 4 | 実際のコードを呼ぶスクリプトやテストを実行した |
| 5 | 動いているアプリで再現した |

共有コードに触らない小さな変更なら、この段階は「影響範囲は diff 内に閉じている」と根拠つきで書いて終えてよい。

### 6. 実ブラウザ検証

`diff.touchesUi` が true のときだけ実行する。false なら「UI への変更なし」として飛ばす。Playwright が使えるかは `playwrightAvailable` で見る（`project` か `environment` なら使える。`playwrightInstalled` はプロジェクトの依存にあるかどうかだけを示す）。

`references/browser-check.md` に従い、開発サーバーを起動して、変更した画面を Playwright で実際に操作する。要件の各項目を画面上で確かめ、コンソールエラー、失敗したリクエスト、モバイル幅とデスクトップ幅のスクリーンショットを証拠として `.dokumi/shots/` に残す。開発サーバーのないプロジェクト（ブラウザ拡張機能など）の開き方も同じファイルにある。

操作を書く前に、要件の番号と確認項目の対応表を作る（同ファイルの 1）。確認項目には要件の番号を付け、どの番号にも確認項目がない要件を、スクリプトの出力（`uncovered`）で洗い出す。思いついた項目だけを確かめて全部通っても、確かめなかった要件については何も分かっていない。

axe による自動のアクセシビリティ検査もここで実行する。プロジェクトにも環境にも axe がなければ、プロジェクトの外に取得して使う（`references/axe.md`）。

既存の E2E テストが通ることは、この段階の代わりにならない。今回の変更で増えた振る舞いを、自分で操作して確かめる。

位置、高さ、折り返しのように配置を測る確認は、1 つの条件で済ませない。表示される文字列の長さや要素の数が変わる条件を複数試す（`references/browser-check.md` の「配置を測るとき」）。1 条件で「崩れない」と確かめても、別の条件では崩れることがある。

開発サーバーを起動できない、または画面に到達できない（認証や外部 API が必要など）場合は、できた範囲と止まった理由を書き、判定を ESCALATE 寄りにする。確かめていないものを確かめたと書かない。

### 7. フロントエンド観点

`references/frontend-checklist.md` を読み、diff と段階 6 の結果に照らして確認する。状態の網羅、アクセシビリティ、レスポンシブ、フレームワーク特有のミス、型の規律、デザインの一貫性、差分の最小性、バンドルへの影響。

ここでも原則 1 が効く。blocker にするには証拠が要る（axe の違反出力、はみ出したスクリーンショット、再現手順）。読んで気づいただけの懸念は warning。

### 8. 判定とレポート

`references/report-format.md` の形式で `.dokumi/report.md`（人向け）と `.dokumi/report.json`（エージェント向け）を書く。

判定の前に、要件の番号ごとに、何を実行して確かめたかを表にする（レポートの「要件ごとの確認」）。実行した証拠を挙げられない要件は「未確認」とし、選ばずに全部を「未証明・未確認」に載せる。未確認の要件が要件の中心にかかわるなら、下の規則どおり ESCALATE にする。

| 判定 | 条件 | 次の動き |
|---|---|---|
| **PASS** | blocker が 0 件（`onWarning: ask` のときは、判断が要る warning も 0 件） | PR を作ってよい。`report.md` の PR 用の節を PR 本文に入れる。warning と未証明の項目は隠さず載せる。 |
| **FIX** | blocker が 1 件以上あり、修正方法が明確 | 生成エージェント（自分なら自分）が `report.json` の指摘を修正し、再検証する。 |
| **ESCALATE** | 2 回修正しても blocker が残る／要件の解釈が割れている／修正に仕様判断が要る／検証そのものを完遂できなかった／`onWarning: ask` で判断が要る warning がある | PR を作らず、人に判断を求める。何を決めてほしいかを 1 つずつ書く。 |

条件が重なったときは **ESCALATE を優先する**。直し方が明確な blocker があっても、次のどれかに当たれば FIX ではなく ESCALATE にする。

- 要件の解釈が割れていて、どちらを採るかで実装が変わる箇所が 1 件でもある
- blocker のうち 1 件でも、直し方が仕様の判断に依存する
- 要件の中心にかかわる項目を確かめられなかった

人の判断を待たずに一部だけ直すと、判断の結果で直した箇所をもう一度変えることになる。ESCALATE のレポートには、判断を待たずに直せる blocker とその直し方も載せ、「決めてほしいこと」と分けて書く。解釈が割れていても、どちらを採っても実装が変わらない箇所は、判定に影響させず warning に載せる。

**修正と再検証は最大 2 回。** 再検証では次をやり直す。

| やり直す段階 | 対象 |
|---|---|
| 1 と 2 | 全体。修正が別の箇所を壊していないか |
| 3（独立レビュー） | 修正の差分。blocker がどの段階で出たものでも省かない |
| blocker が出た段階 | その blocker（mutator は `--only <key>` で該当ミュータントだけを数秒で再確認できる） |

段階 3 を毎回やり直すのは、直したばかりのコードが、直した意図どおりに読めてしまうため（原則 3）。機械ゲートと実ブラウザが通った後でも、独立レビューは修正の中の食い違いを見つける。依頼文は `references/reviewer-briefs.md` の「修正の再検証」。修正の差分は、前の回の終わりに記録した状態と比べて取る（`references/proving.md` の「回をまたいで差分を取る」）。

修正の中で要件や仕様書の文を足した・書き換えたなら、その文は次から要件になる。`.dokumi/requirements.md` に番号を振って足し、独立レビューに 1 文ずつ確かめさせる。書いた本人には、その文がどこまでの範囲を約束しているかが見えにくい（「失敗はダイアログで知らせる」と 1 文足すと、失敗し得る操作のすべてがその対象になる）。

回数の上限は、人の判断を挟まずに修正を繰り返す回数に掛かる。ESCALATE に人が答えた後の検証や、ユーザーが改めて頼んだ検証は、1 回目から数え直す。

FIX を出す前に、`fix` に書く直し方をコピーの上で試し、それで blocker が解消して既存のテストも通ることを確かめる（`references/proving.md` の「壊して確かめる・直して確かめる」）。試していない直し方は、そうと分かるように書く。

2 回で直らないものを 3 回目に回さない。同じ前提に立った修正が 2 度同じ検査で落ちたなら、修正ではなく前提が間違っている。それは人が見るべき状況。

blocker を消すためにテストを消す、skip する、検査設定を緩める、`mutator accept` を自分で実行する、のはいずれも修正ではない。段階 2 が次の回でそれを検出する。

最後に、検証対象を変えていないこと（`.dokumi/before.patch` との一致）と、起動したサーバーや worktree を片付けたことを確かめる。次の回に修正の差分を取れるよう、検証した状態も記録する（`references/proving.md` の「回をまたいで差分を取る」）。

レポートのファイルを書けない環境（ファイル書き込みが制限されたサブエージェントなど）では、`report.md` と `report.json` の全文を最終メッセージに載せる。
