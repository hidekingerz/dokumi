# 実プロジェクトでの試用記録: chrome-bookmark-list（リポジトリ全体）

dokumi を、Chrome 拡張機能 chrome-bookmark-list のリポジトリ全体に 5 回当てた記録。1 つの PR の差分ではなく、`src/` 全体を対象にした。

前半は、スキルを実行したエージェントが書いたフィードバックレポートをそのまま載せたもの（見出しを 1 段下げた以外は変えていない）。文中の `SKILL.md:267` などの行番号は、試用時点の版のもの。後半に、このフィードバックを受けて手順に反映したことを足してある。

---

dokumi スキルを、実際のリポジトリの検証と修正に通しで使った結果の報告です。書いたのは、スキルを実行したエージェント（Claude）です。

### 1. 結論

- **有用だった。** 既存のテスト 647 件・カバレッジ 97% が通っていた状態から、実害のある不具合を複数見つけ、直すところまで進められた。効いたのは「実ブラウザで確かめる」「評価者を生成者から切り離す」「ミューテーションテスト」の 3 つ。
- **いちばんの弱点は、PASS の意味が確認項目の範囲に限られること。** 同じコードに対して 2 回目は PASS、3 回目は blocker 5 件だった。差は、エージェントが 3 回目に確認対象を広げたことだけ。漏れを PASS が隠す。
- **コストが大きい。** 利用制限に複数回当たった。主因はリポジトリ全体を対象にしたことで、スキルが想定する「PR の差分」での使い方はまだ試していない。

改善提案は 4 章に、優先度の高い順に書いた。

### 3. 効いたところ

#### 3.1 実ブラウザ検証（段階 6）

- 複数のブックマークをまとめて移動・削除した後の「元に戻す」で並び順が壊れる不具合と、複数選択の並び替えが同じフォルダ内で失敗する不具合を、実際の拡張機能を操作して見つけた。
- 既存のテストは `chrome.bookmarks.move` のモックの呼び出し列を確かめていて、実際の並びは見ていなかった。原因は Chrome の API の規則（同じ親の中では `index` が「動かす前の並びでの位置」になる）で、モックでは再現しない。
- 「確認が失敗したら、システムより先に確認方法を疑う」の原則は実際に効いた。最初に出た不合格 18 件のうち 12 件は、確認スクリプト側の誤りだった（4.8 参照）。

#### 3.2 評価者を生成者から切り離す（段階 3・4）

今回、効果がいちばん大きかった原則。3 回とも、生成者（私）の報告を独立レビューが実行で覆した。

- 2 回目の完了報告「文書は実物どおり」に対し、3 回目のレビューが、内部仕様書に載っていないファイル 8 つを機械的に列挙した。
- 2 回目に私が外部仕様へ書いた「操作の失敗は『エラー』ダイアログで知らせる」に対し、守っていない操作 6 つを再現テストつきで示した。
- 4 回目、私が修正した直後のコードに対して、食い違いを 4 件見つけた。うち 1 件は、複数選択のドラッグが途中で失敗すると、通知も取り消しも出ず画面が古いまま残る、という実害のあるものだった。

レビューの指摘は、自分で再実行したものがすべて再現した。捨てた指摘は 0 件。「指摘のコマンドを自分で再実行する」の手順は、そのまま機能した。

#### 3.3 ミューテーションテスト（段階 4）

- 「仕様の振る舞いを壊しても全件通る」箇所を 9 つ特定できた（HTML エスケープ、検索のデバウンス、ドロップ位置の 40/20/40% の判定など）。
- 5 回目の最後に、「一括移動がブックマークの id を使わなくてもテストが落ちない」という穴が出た。直前に入れた修正（同じ URL のブックマークの取り違え）を守れていない箇所で、コードを読むだけでは気づかなかった。
- 振り分けスクリプトのグループ化（同じ関数の同じ種類の穴を 1 件にまとめる）は、数百件の未検出を読める量に減らすのに役立った。

#### 3.4 そのほか

- 「証明できた指摘だけが blocker」: 指摘が 20 件を超えても、止める理由と判断事項が混ざらなかった。
- 「検証中は直さない」「実験はコピーの上で」: 検証対象の差分が検証前と一致することを毎回確かめられた。修正案をコピーで試してから FIX に書く手順も、落ちる既存テスト 15 件を事前に把握するのに役立った。
- ESCALATE の「決めてほしいこと」: 選択肢と結果を並べる形は機能した。5 回で計 14 件の判断をユーザーが短い返答で決められた。

### 4. 問題と改善提案

#### 4.1 【高】判定が、エージェントの思いついた確認項目の範囲に限られる

- **起きたこと**: 2 回目は PASS、3 回目は同じコードで blocker 5 件。3 回目に、仕様書の §12〜§17（コンテキストメニュー、複数選択、取り消しなど）を実ブラウザの確認対象に足したら、不具合が出た。2 回目の PASS は「確認した 62 項目は通った」という意味でしかなかった。
- **原因と思う箇所**: 段階 6 は「要件の各項目を画面上で確かめる」とあるが、どの要件に確認項目が無いかを出す仕組みがない。レポートの「未証明・未確認」も、エージェントが自分で気づいた分しか載らない。
- **提案**: 段階 6 の最初に、要件（仕様書の節や受け入れ条件）と確認項目の対応表を作らせる。確認項目が 1 つも無い要件は、レポートの「未証明・未確認」に機械的に載せる。要件の中心にかかわるものが残っていれば、既存の規則どおり ESCALATE 寄りにする。

#### 4.2 【高】修正後の再検証で、独立レビューのやり直しが必須になっていない

- **起きたこと**: 4 回目、3 回目の blocker をすべて直して機械ゲートと実ブラウザが通った後に、念のため要件適合の独立レビューをかけたら、食い違いが 4 件出た。
- **原因と思う箇所**: `SKILL.md:267`「再検証では段階 1 と、blocker が出た段階をやり直す」。段階 6・7 で出た blocker を直した場合、段階 3 はやり直しの対象にならない。
- **もう 1 つの型**: 修正の一部としてエージェントが仕様書に文を足すと、その文が次の回の「要件」になる。2 回目に私が書いた 1 文が 3 回目の blocker になり、4 回目に書き足した文が同じ回のレビューで食い違いになった。書いた本人には、文の適用範囲の広さが見えない。
- **提案**:
  - 再検証では、修正の差分に対して段階 3 の独立レビューを必ずやり直す。
  - 修正で要件や仕様書を変えた場合は、変えた文を 1 つずつ「この文が当てはまる操作をすべて挙げ、実行で確かめる」対象にする、と依頼文（`references/reviewer-briefs.md`）に足す。

#### 4.3 【高】axe が無いと、アクセシビリティが未検査のまま PASS になる

- **起きたこと**: `references/browser-check.md:185` の「どちらもなければ依存を足さず、未実施と書く」に従い、1〜3 回目は axe を回さなかった。ユーザーに「axe を入れるか」と聞かれて初めて回したところ、serious の違反が 3 種類出た（ダイアログに名前がない、コントラスト不足、見えている文字が読み上げ用の名前に入っていない）。
- **提案**:
  - axe が無いときは、プロジェクトの依存を変えずに外へ取得して回す手順を既定にする（`npm pack axe-core` を作業用ディレクトリで実行し、`axe.min.js` を読み込む）。今回この方法で問題なく動いた。
  - 読み込み方について。記述は `page.addScriptTag({ path })` だが、今回は `page.evaluate` の中でソースを評価した。拡張機能のページ（Manifest V3）は CSP が厳しいので、`addScriptTag` が通るかは試していない。
  - axe が「要確認」とする項目（グラデーションの上の文字、1〜2 文字の文字列）は数が多い（今回 31〜40 要素）。計算済みの色から自前で比を測る手順を参照文書に入れると、未確認が減る。今回は 52 種類を測れた。
  - ホバー中の配色は、マウスの位置にある要素しか測れない。網羅できないことを明記したほうがよい。

#### 4.4 【中】blocker の説明が文章だけで、人が状況をつかみにくい

- **起きたこと**:
  - 1 回目の「決めてほしいこと」の 1 件に、ユーザーが「理解できなかったので説明を求める」と返した。判断を仰ぐための説明が、判断できる形になっていなかった。
  - 3 回目の並び順の不具合（下の例）は、「いつ・どの値を読んだせいで・どう並ぶか」が要点だが、レポートでは文章と配列の出力だけで説明した。手順と状態が絡む不具合は、文章だと読み手が頭の中で順番を組み立て直すことになる。
- **原因と思う箇所**: `references/report-format.md` の blocker の書式は、場所・内容・証拠・実害・直し方の箇条書きで、図についての指針がない。
- **提案**: blocker（と、判断が要る warning）の説明に、必要に応じて Mermaid の図を付ける、と `references/report-format.md` に足す。`report.md` は PR 本文になるので、GitHub 上でそのまま図として表示される。

  **付ける場合**
  - 複数の手順や複数の登場者（利用者・アプリ・外部の API）をまたぐ不具合。操作の順序、状態の移り変わり、データの流れが要点のもの
  - 「期待」と「実際」の違いが、並びや状態の違いとして現れるもの
  - 判断が要る項目で、選択肢ごとに動作がどう変わるかを見せたいもの

  **付けない場合**
  - 1〜2 行で言い切れる事実（設定値の誤り、ファイルの記載漏れ、文言の違いなど）。図にすると、かえって読む量が増える

  **図の種類の目安**
  | 伝えたいこと | 図 |
  |---|---|
  | 操作と API 呼び出しの順序、どの時点の値を使ったか | `sequenceDiagram` |
  | 状態の移り変わりと、想定していない遷移 | `stateDiagram-v2` |
  | 分岐のどこで期待から外れるか、選択肢ごとの結果 | `flowchart` |

  **守ること（原則 1・2 との整合）**
  - 図は証拠の代わりにしない。再現のコマンドと出力は、これまでどおり必ず載せる
  - 図に書く値は、実行で得た値だけにする。推測した経路や、確かめていない状態を描かない
  - 図と証拠の出力が食い違わないこと。直した後の再検証では、図も実際の動作に合わせて直す
  - 1 つの blocker に図は 1 つ、登場者は 3〜4、手順は 10 前後まで。それを超えるなら、不具合を分けるか、図をやめて表にする
  - 記法が崩れると図が表示されないので、基本の記法だけを使う。確かめる手段（Mermaid の CLI など）が環境にあれば通す。無ければ依存を足さず、その旨を書く

  **例（3 回目の並び順の不具合）**

  フォルダに W1・W2・W3・W4 が並んでいて、W1 と W2 を一括で別のフォルダへ移し、「元に戻す」を押した場合。

  ```mermaid
  sequenceDiagram
      participant U as 利用者
      participant A as 拡張機能
      participant C as Chrome のブックマーク

      Note over C: フォルダ内は W1, W2, W3, W4
      U->>A: W1 と W2 を選んで一括移動
      A->>C: W1 の位置を読む
      C-->>A: 0
      A->>C: W1 を移動
      Note over C: フォルダ内は W2, W3, W4
      A->>C: W2 の位置を読む
      C-->>A: 0（W1 が抜けた後の位置。元は 1）
      A->>C: W2 を移動
      U->>A: 元に戻す
      A->>C: W1 を位置 0 へ戻す
      A->>C: W2 を位置 0 へ戻す
      Note over C: フォルダ内は W2, W1, W3, W4（元と違う）
  ```

  文章では「1 件ずつ動かしながら位置を読むので、後の項目の位置がずれて記録される」の 1 文になる。図にすると、どの時点の読み取りが誤りの元かが一目で分かる。
- **`report.json` との関係**: 図は人向けなので `report.md` にだけ載せ、`report.json` には入れない（エージェント向けには `fix` と `evidence` があれば足りる）。

#### 4.5 【中】リポジトリ全体を対象にする使い方の指針がない

- **起きたこと**: ユーザーが「全体に対して」と指示した。スキルは差分を前提に書かれているので、次の点を都度判断することになった。
  - `mutator --since` が使えず、全体実行になる。記述の `--time-budget 300` では足りず、1500 秒でも 1 回は 46 件が未実行で残った（1700 秒で 2,760 件を完走）。1 回あたり 25〜30 分。
  - 「修正と再検証は最大 2 回」は守れなかった（5 回）。
  - 重大度の表の「axe の critical / serious 違反（**変更した要素**）」（`references/browser-check.md:207`）が、全体対象では何を指すのか決まらない。今回は「今回の変更で増えた要素に当たるものだけ blocker、変更前からあるものは warning」と自分で決めた。
- **提案**: 全体を対象にする場合の節を足す。範囲を機能や仕様の節で区切って回すこと、変更前からある不具合の重大度の決め方、時間枠の目安を書く。

#### 4.6 【中】mutator まわり

- **版の違い**: スキルの記述は v0.4.0、入っていたのは 0.3.0。出力の形（`gaps` の `gap` が `notReached` / `notDetected` / `notInfected`）は 0.3.0 で読めたが、フィールド名を一度読み違えた。振り分け結果（`mutants-triage.json`）のグループの形を `references/mutation.md` に例示してほしい。
- **受け入れの流れ**: ソースを編集するとキーが変わり得るので、`mutator accept` の前に対象ファイルを再実行してキーを取り直す必要があった。また、`accept` は直近の実行結果がある場所で実行する必要がある（今回はコピーの上で実行し、`mutator.accepted.json` を本体へ移した）。この手順が書かれていない。
- **同じ行の別のミュータント**: 「この行の未到達を受け入れる」つもりで行番号で拾うと、同じ行の別の未検出まで入る。`gap` の種類と書き換えの内容で絞る必要がある、と注意書きがほしい。
- **テストとの対応が取れない未検出**: JSDOM の上で本物のレンダラを動かすテスト（今回は axe のテスト）が検出している書き換えを、mutator は未検出と報告した。コピーの上で手で壊すと、そのテストは落ちた。「未検出と出ても、該当しそうなテストがあるなら手で壊して確かめる」を手順に入れるとよい。
- **`mutator accept` の了承**: スキルは「エージェントは実行しない」としている。今回はユーザーが方針に同意したので実行したが、私の質問が「方針でよいか」と「実行してよいか」を 1 つにまとめていて、了承の範囲が曖昧になった。「accept の実行は、方針とは別に明示の了承を取る」と書いてほしい。

#### 4.7 【中】スキル自身と作業ファイルが、プロジェクトの検査に混ざる

- **テストの探索**: プロジェクトの Vitest に `include` の指定が無かったため、リポジトリ内に置いたスキルの評価用フィクスチャ（`.claude/skills/dokumi/evals` 以下の `*.test.ts`）をプロジェクトのテストとして拾った。1 回目の blocker の 1 つがこれだった。
- **lint**: `.dokumi/` の作業ファイル（確認スクリプト、独立レビューの再現テスト）を、プロジェクトの Biome が `npm run check` / `lint` / `format` の対象にした。レビューが書いた再現テストの import の並びで、機械ゲートが 1 回落ちた。
- **提案**:
  - 段階 0 で、プロジェクトのテストランナーと lint が `.dokumi/` と `.claude/skills/` を拾うかを確かめ、拾うなら警告する。
  - 再現テストやスクリプトの置き場所を、検査の対象外になる場所に決める（スクラッチ用のディレクトリなど）。
  - 独立レビューへの依頼文に「作業ツリーに書くファイルはプロジェクトの lint を通すか、対象外の場所に置く」を足す。

#### 4.8 【中】`references/browser-check.md` に足したい落とし穴

今回、最初の不合格 18 件のうち 12 件が確認側の誤りだった。次の 5 つは一般的に起きるはず。

- Playwright の `dragTo` は、ドラッグの途中でページをスクロールし、掴む対象がずれることがある。viewport を縦に広げてスクロールを無くし、`page.mouse.move/down/up` を自分で組み立てる。
- スクロール直後の右クリックは、スクロールでメニューを閉じる実装だとメニューが出ない。スクロール後に少し待つ。
- 修飾キーつきクリックの意味はアプリごとに違う。今回は Cmd+クリックが「バックグラウンドで開く」で、複数選択にならなかった。確認スクリプトがこれで「複数選択の状態」を作ったつもりになり、その状態を検査できていなかった（axe の回で発覚）。**状態を作ったら、検査の前にその状態になっていることを確かめる**、を原則として書いてほしい。
- macOS では Ctrl+クリックが右クリック扱いになる。Ctrl 系の操作は macOS では確かめられない。
- 前の確認の失敗が次の確認に持ち越される。確認ごとにデータを作り直す。

拡張機能に固有の点: `launchPersistentContext` に `--load-extension` を渡せば、`chrome://newtab/` を実際の `chrome.bookmarks` / `history` / `sessions` つきで操作できる。開発サーバーを前提にした記述が多いので、拡張機能の例があると助かる。

#### 4.9 【低】そのほか

- **ごまかし検出の誤検出**: 「スタブ」の検出が、`placeholder` を含む文字列やクラス名を 18 件拾った。属性名や CSS のクラス名は除外できるとよい。
- **カバレッジ**: テスト用の共通部品（`test/helpers/`）を足したら、プロジェクトのカバレッジ設定の除外パターンに掛からず、製品コードの数字が下がって見えた。しきい値のある設定を変えることになるので、「計測対象を製品コードに合わせる変更」と「しきい値を下げる変更」を、段階 2 の「検査設定の変更」で区別する指針がほしい。
- **判断事項の数**: 5 回で 14 件。1 回に 5〜6 件出ると、ユーザーの返答が「1 表示中だけ、2 寄せる…」と番号だけになる。番号と短い答えで意図が通じる書き方（各項目が単独で読める、推奨を先に置く）を `references/report-format.md` で徹底するとよい。
- **再検証の段階の表**: 回を重ねると「前の回から手を付けていない warning」が溜まる。持ち越しを別の節に分ける形式があると、レポートが読みやすい。

### 5. コストの記録

| 項目 | 実績 |
|---|---|
| mutator の全体実行 | 1 回 25〜30 分。3〜5 回目で 4 回 |
| 実ブラウザの確認 | 3 本（62 項目・74 項目・axe 38 状態）で 1 回 8〜10 分。最終的に各 4〜5 回 |
| 独立レビュー（仕様照合、4 回目） | 約 29 万トークン |
| テストの書き換えを任せたエージェント（修正側） | 約 34 万トークン |
| 利用制限 | 作業中に複数回到達。うち 1 回は独立レビューが途中で止まり、再開した |

修正の作業（テストの書き換えなど）は dokumi の外の話だが、ESCALATE → 判断 → 修正 → 再検証の 1 周が重いことは、スキルの使い勝手に直結する。

### 6. この報告の限界

- 差分を対象にした本来の使い方（1 つの PR の検証）は試していない。コストと見つかり方は、そこでは大きく違うはず。
- 1 つのリポジトリ、1 つのエージェントでの結果。フレームワークを使わない拡張機能という、やや特殊な対象だった。
- 1・2 回目の細部は、作業中に会話の文脈が要約されたため、当時の記録（レポートとログ）から書いている。
- 提案はどれも試していない。今回の経過から考えた案である。

### 確かめて分かったこと

- **`page.addScriptTag({ path })` は、CSP の厳しいページでは実際に拒否される。** `script-src 'self'` のページと、対象の拡張機能のページ（`chrome://newtab/` の置き換え）の両方で試し、どちらも「インラインスクリプトの実行は CSP に反する」で失敗した。`page.evaluate` にソースを渡す方法は、どちらでも動いた。それまでの手順書の記述（`addScriptTag` で読み込む）は、拡張機能では動かなかったことになる。
- **`mutator accept` が照合するのは、直近の実行結果ではなく、今のソース。** 0.3.0 の実装は、実行したディレクトリのソースからミュータントを列挙して key を引く。ソースを編集した後に key が合わなくなるのはこのため。記録（`mutator.accepted.json`）も実行したディレクトリに書かれる。
- **新しく作られた `mutator.accepted.json` を、段階 2 は検出していなかった。** 検査の対象が「変更された設定ファイル」だけで、新規に追加されたものと未追跡のものが漏れていた。「エージェントが自分で受け入れたら次の回に検出される」という手順書の前提が成り立っていなかったので、`mutants-accepted` として検出するようにした。
- **フィードバックの例の図は、そのまま描画できた。** 提案の時点では描画を確かめていなかったので、Mermaid 11.17.2 で描画し、画像を見て、矢印の順番と注記が意図どおりであることを確かめた。壊れた記法と、閉じていないブロックは、スクリプトが検出する。
- **スタブの誤検出 18 件は、直した後 0 件になった。** 対象リポジトリの全ファイルで確かめた。18 件はすべて CSS のクラス名、定数名、変数名、コメント中の語だった。
- **スキルのディレクトリが対象リポジトリで未追跡のままだと、スキル自身のファイルが変更に数えられていた。** 試験用の `*.tsx` のせいで、「UI に触る変更」の判定も常に真になっていた。

### 採らなかった提案と、違う形にした提案

- **再現テストの置き場所を、検査の対象外の場所に移す（4.7）。** 採らなかった。`.dokumi/review/` は、プロジェクトの設定を引き継ぐテスト設定や、開発サーバーから配信する検証用ページの前提になっている。置き場所は変えず、機械ゲートの側で、作業ファイルだけで落ちた場合の扱いを決めた。独立レビューの依頼文に「lint を通す」と足す案も、同じ理由で採っていない。
- **全体を対象にしたときの、変更前からある問題の重大度（4.5）。** 試用では「今回の変更で増えた要素に当たるものだけ blocker、前からあるものは warning」と判断していた。手順書では、1 回目は範囲に入るコードの全部を「変更」として扱い、前からある問題も表のとおりに blocker にする、とした。全体の検証を頼む目的が既存の問題を見つけることなので、「前からあった」を理由に下げると何も止まらなくなるため。再検証で、前の回に行わなかった検査（axe など）を足して見つかったものも同じ扱いにした。ここは運用して合わなければ見直す。
- **「修正と再検証は最大 2 回」（4.5）。** 上限は変えず、何を数えるかを書いた。人の判断を挟まずに修正を繰り返す回数に掛かり、人が ESCALATE に答えた後は数え直す。試用の 5 回は、この数え方では上限を超えていない。

- **図は、端末では表示されない（4.4）。** 提案は `report.md` が GitHub で表示されることを前提にしているが、FIX や ESCALATE のレポートは、PR になる前に端末やエディタで読まれる。そこで、図の前に同じ内容を 1 文で書くことを必須にし、会話の中では図のソースを貼らずその 1 文を使う、とした。図を確かめる手段がないときに「その旨を書く」のは提案どおり。

### 反映した手順の試験

- **スクリプトは試験を書いてから直した。** `eval-fixtures/script-tests.sh` に 15 項目（スタブの誤検出、`--all`、受け入れの記録の検出、スキル自身と作業ファイルの除外）。直す前のスクリプトでは 11 項目が落ち、直した後は全部通る。
- **手順書の 2 か所は、旧版と新版を別々のエージェントに読ませて比べた**（実行はさせず、手順書を読んで答えさせる机上の演習。旧版 1 体、新版 2 体ずつ）。
  - 再検証でやり直す段階：blocker が段階 6 と 7 で出て、修正の中で仕様書に 1 文を足した、という状況。旧版は「手順書の文言どおりなら段階 3 は対象外」と読み、足した 1 文を要件として扱わなかった。新版は 2 体とも、修正の差分に独立レビューをかけ、足した 1 文を番号つきの要件にして、当てはまる操作を列挙させると答えた。
  - 確認項目のない要件の扱い：要件 8 項目のうち 3 項目に実行の証拠がない結果一式を渡して、レポートを書かせた。**旧版でも ESCALATE になり、3 項目を未確認として挙げた。** 差が出たのは形だけで、新版は 2 体とも、判定の次の行に「8 項目中 5 項目を確かめた」と書き、「要件ごとの確認」の表を出した。漏れが入力の中に見えている状況では、旧版でも気づく。試用で起きたのは、確認項目を自分で作る段階で節が丸ごと抜け、それに気づかないことだった。その再現は机上ではできていない。
