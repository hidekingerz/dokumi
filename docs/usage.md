# dokumi の使い方

AI エージェントが書いたフロントエンドの変更を、PR を作る前に検証するスキル。何を見てどう判定するかは [判定基準](criteria.md) にある。

## 必要なもの

| 用途 | 必要なもの | ないとき |
|---|---|---|
| 基本 | Node.js 18 以上、git、`package.json` のあるフロントエンドのプロジェクト | 使えない |
| テストの質の実測 | Node.js 24 以上、Vitest 5、[mutator](https://github.com/mizchi/mutator) 0.4.0 | 手動の抜き取り検査に切り替わる（網羅ではなくなる） |
| 実ブラウザ検証 | Playwright と Chromium、起動できる開発サーバー（ブラウザ拡張機能は、ビルドした出力を読み込んで開く） | その段階は「未実施」と報告される |
| アクセシビリティの自動検査 | axe-core。プロジェクトにも環境にもなければ、`.dokumi/tools/` に取得して使う（プロジェクトの依存は変わらない） | ネットワークに出られないときだけ「未実施」と報告される |

mutator がプロジェクトに入っていない場合：

- npm のプロジェクトでは、`package.json` を変えずに一時的に入れて使う。
- pnpm / yarn / bun のプロジェクトでは、勝手に依存を足さず、手動の抜き取り検査に切り替えてレポートで導入を提案する。実測を使いたければ、先に `@mizchi/mutator@0.4.0` を `devDependencies` に入れておく。

## 導入

`.claude/skills/dokumi/` を、対象リポジトリの `.claude/skills/` にコピーする。全リポジトリで使うなら `~/.claude/skills/` に置く。

```sh
rsync -a --exclude evals <このリポジトリ>/.claude/skills/dokumi <対象リポジトリ>/.claude/skills/
```

`evals/`（試験ケース）はコピーしない。動作に不要なうえ、中に `*.test.tsx` があり、対象リポジトリのテストランナーが `include` を絞っていないと、プロジェクトのテストとして拾われる。

## 呼び出し方

エージェントに実装させた後、PR を作る前に頼む。

```
PR 前に dokumi で検証して
```

検証には 3 つの入力が要る。会話の中にあればそれが使われ、なければ尋ねられる。

| 入力 | 内容 |
|---|---|
| 要件 | 元の指示、issue、仕様。これがないと要件を満たしたか判定できない |
| 変更 | ベースブランチからの差分。未コミットのファイルと新規ファイルも対象 |
| 完了報告 | 実装したエージェントが「やった」と言っている内容 |

ベースブランチは `origin/main`、`origin/master`、`origin/develop`、`main`、`master` の順に自動で探す。違うなら「ベースは `release/1.2`」のように伝える。モノレポでは対象のパッケージを伝える。

所要時間は 1 回あたり 5〜10 分程度（試験での実測。変更の大きさと実ブラウザ検証の有無で変わる）。

### リポジトリ全体を対象にするとき

dokumi は 1 つの変更（diff）を検証するように作ってある。既存のコード全体を検証させたいときは、そう伝える。

```
リポジトリ全体を dokumi で検証して。要件は docs/spec.md
```

全体の検証は重い。ソース 45 ファイルのリポジトリでの実測では、ミューテーションテストの全体実行だけで 1 回 25〜30 分、独立レビューが約 29 万トークンかかり、利用制限に何度か当たった。そのため、仕様書の節や機能で範囲を区切って、1 回ずつ進める。区切り方は検証の前に示される。詳しくは [試用記録](eval-chrome-bookmark-list-2026-11-22.md)。

## 結果の見方

対象リポジトリの `.dokumi/` に出る。このディレクトリはローカルでだけ無視される設定になり、コミットにも PR にも入らない。

| ファイル | 読み手 | 内容 |
|---|---|---|
| `.dokumi/report.md` | 人 | 判定、要約、段階ごとの結果、指摘と証拠、人が見るべき箇所 |
| `.dokumi/report.json` | エージェント | 指摘ごとの重大度、場所、直し方、再確認コマンド |
| `.dokumi/checks.md` | 人 | 要件の番号と、それを確かめる操作の対応表 |
| `.dokumi/shots/` | 人 | 実ブラウザ検証のスクリーンショット |
| `.dokumi/review/` | 人 | 指摘の証拠になった再現テストとログ |

判定は 3 種類。

| 判定 | 意味 | 次にすること |
|---|---|---|
| **PASS** | PR を止める問題がない | PR を作る。`report.md` 末尾の「検証（dokumi）」の節を PR 本文に入れる |
| **FIX** | 実行で証明された問題がある | エージェントに `report.json` の指摘を直させ、もう一度検証する。最大 2 回まで |
| **ESCALATE** | 人の判断が要る | レポートの「決めてほしいこと」に答える |

**PASS は「確かめた項目は通った」という意味で、確かめなかった要件については何も言っていない。** 判定の次の行に、要件のうち何項目を確かめたかが書かれる。レポートの「要件ごとの確認」には、要件の番号ごとに、何を実行して確かめたかが並ぶ。「未確認」の行は、問題がないと分かったわけではない。同じコードをもう一度検証させると、確認の範囲が広がって新しい問題が出ることがある。

指摘の重大度は 3 段階。

| 重大度 | 意味 |
|---|---|
| blocker | 実行で証明された問題。PR を止める |
| warning | 証明できていない懸念、または止めるほどではない問題。PR 本文に載る |
| note | 参考情報、変更前からあった問題。PR 本文には載らない |

手順や状態が絡む不具合と判断事項には、説明の図（Mermaid）が付くことがある。図は説明で、証拠は別に載っているコマンドと出力のほう。図の前に同じ内容が 1 文で書かれるので、端末で読むときはその 1 文を読む。

blocker には「実害」の行が付く。要件に反すると証明できたことと、今のデータで実際に起きていることは別なので、「確認済み」「現在は未発生」「未確認」のどれかが書かれる。直す順番はこの行で決める。要件に「実データで確かめる」条件があるなら、検証を頼むときにデータの場所を伝えておくと、ここが「未確認」で止まらない。

warning のうち「判断が要る」と付いたものは、レビューで必ず見てほしいもの（自動テストなしの変更、等価ミュータントの受け入れ提案、要件にない変更、要件の中心にかかわる未確認）。

レポートの「未証明・未確認」は、検証が確かめられなかった範囲。ここに書かれた項目は、問題がないと確認されたわけではない。

## 厳しさの切り替え

2 つの設定がある。

| 設定 | 値 | 動き |
|---|---|---|
| `mode` | `standard`（既定） | 変更の振る舞いを、どのレベルでも確かめた証拠がないときに止める。自動テストがなくても、実ブラウザ検証などで確かめてあれば warning |
| | `strict` | 変更したコードをどのテストも実行していなければ止める。ライブラリや、ロジック中心のコード向け |
| `onWarning` | `report`（既定） | warning は PR 本文に載せ、レビューで判断する |
| | `ask` | 判断が要る warning があれば、PR を作る前に確認を求める（判定は ESCALATE） |

`ask` は人がその場にいる作業向け。夜間などの無人の実行で使うと、確認待ちで止まったままになる。

指定の方法は 2 つ。両方あれば呼び出し時の指示が優先される。

**呼び出し時に伝える**

```
strict で検証して
warning は PR の前に確認して
```

**プロジェクト直下に `dokumi.config.json` を置く**

```json
{ "mode": "strict", "onWarning": "report" }
```

モードより先に、プロジェクト自身の基準が使われる。次の設定があれば、モードに関係なく検査され、満たさなければ止まる。

- テストフレームワークのカバレッジのしきい値（Vitest の `coverage.thresholds`、Jest の `coverageThreshold` など）
- mutator の重要領域（`critical`）としきい値（`thresholds.break`）

認証、権限、金額計算など「必ずテストで守りたい場所」は、モードを `strict` にするより、mutator の重要領域に指定するほうが的を絞れる。

```ts
// mutator.config.ts
export default defineConfig({ critical: ['src/auth/**', 'src/billing/**'] });
```

## 等価ミュータントの受け入れ

mutator が「テストが気づかない」と報告した書き換えのうち、どんな入力でも元と区別できないものがある（決して null にならない値への `?.` など）。エージェントはこれを自分では受け入れず、レポートの「受け入れ提案」に理由つきで載せる。

納得できれば、人が次を実行する。記録は `mutator.accepted.json` に入り、コミットして共有する。

```sh
npx mutator accept <key> --reason "<なぜどの入力でも観測できないか>"
```

実行をエージェントに任せてもよい。その場合エージェントは、受け入れる key の一覧（場所、書き換え、理由）を示して、実行してよいかを改めて尋ねる。「等価なものは受け入れる方針でよい」と答えただけでは実行されない。

## やらないこと

- **PR の作成、push、マージはしない。** 判定を出すところまで。
- **検証対象のコードは書き換えない。** 壊して確かめる、直し方を試す、といった実験はコピーの上で行う。修正は判定の後、実装したエージェントの仕事。
- **プロジェクトに依存を足さない。** mutator や Playwright がなければ、その検査を「未実施」と報告する。axe は `.dokumi/tools/` に取得して使うが、`package.json` もロックファイルも変えない。
- **スタイル、命名、好みは指摘しない。**

## 知っておくこと

- **実装したエージェント自身に検証させたときの甘さは、試験できていない。** 設計上は、要件適合とテストの質の判定を別エージェントに任せて補う。別エージェントを起動できない環境では、レポートに「独立レビューなし」と書かれる。その場合は割り引いて読む。
- **試験した構成は React + Vite + Vitest 5 + npm の 1 つだけ。** Next.js、pnpm、Jest などでは、検出や手順が合わない箇所があり得る。
- **問題を見つける力は、試験ではスキルなしの検証と同じだった。** スキルで変わるのは、毎回同じ形のレポートと機械可読な指摘一覧が出ること、検証対象に触れないこと。時間は約 2 倍かかる。詳しくは [作業レポート](work-report-2026-11-19.md)。

- **判定は、確かめた項目の範囲でしか意味を持たない。** 実プロジェクトでの試用では、同じコードに対して 2 回目が PASS、確認の範囲を広げた 3 回目が blocker 5 件だった。レポートの「要件ごとの確認」と「未証明・未確認」を読んで、何が確かめられていないかを見る。
- **修正のたびに、独立レビューがやり直される。** 直した直後のコードは、直したエージェントには意図どおりに見える。試用では、機械ゲートと実ブラウザが通った後の独立レビューが、修正の中の食い違いを 4 件見つけた。その分、再検証にも時間とトークンがかかる。

## うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| ベースブランチを特定できない | ベースを伝える（「ベースは `develop`」） |
| mutator が「テストが失敗」と言うが `npm test` は通る | mutator をプロジェクトの外から実行している。プロジェクトの `node_modules` に入れてから実行する |
| mutator が使えないと言われる | Node.js が 24 未満、または Vitest が 5 未満。手動の抜き取り検査に切り替わる |
| 実ブラウザ検証が「未実施」になる | 開発サーバーを起動できない（環境変数や外部 API が必要）、または Playwright がない。モックの手段を用意するか、手元で確かめる |
| カバレッジのしきい値が「未検査」になる | しきい値は設定されているが、カバレッジを測る手段（`@vitest/coverage-v8` など）が入っていない |
| テストや lint が、`.dokumi/` や `.claude/skills/` の中のファイルで落ちる | 検証の作業ファイルやスキルの試験ケースを、プロジェクトのテストランナーや lint が拾っている。dokumi はそのパスを除いて検査をやり直すが、プロジェクトの設定（Vitest の `include` / `exclude`、lint の対象）で除外しておくと確実 |
| アクセシビリティの自動検査が「未実施」になる | axe を取得できなかった（ネットワークに出られない）。`axe-core` を環境に入れておくか、`AXE_PATH` で `axe.min.js` の場所を渡す |
| FIX が 2 回続いて ESCALATE になった | 同じ前提の修正が 2 度失敗している。修正ではなく前提（要件の解釈や設計）を見直す |
