# dokumi の判定基準

dokumi が何を調べ、何を PR の条件にしているかの一覧。使い方は [使い方](usage.md) にある。

エージェントが実際に従う手順は `.claude/skills/dokumi/SKILL.md` と `references/` にあり、この文書はそれを人が読むためにまとめたもの。食い違いがあれば、手順のほうが実際の動作である。

## 判定の原則

1. **証明できた指摘だけが PR を止める。** blocker にできるのは、実行したコマンドとその出力で示せる問題だけ。コードを読んで怪しいと思っただけのものは warning にとどまる。
2. **実物で確かめる。** 機能を動かし、実際の値を読む。「コンパイルが通る」、エージェントの自己申告、テストが通ることは、変更が正しい証拠として扱わない。
3. **指摘なしは正当な結果。** 何か見つけることは目的ではない。スタイル、命名、好みは対象外。
4. **今回の変更が持ち込んだものだけを見る。** 変更前からあった問題は note として知らせるが、PR は止めない。

## 判定

| 判定 | 条件 |
|---|---|
| **PASS** | blocker が 0 件。`onWarning: ask` のときは、判断が要る warning も 0 件 |
| **FIX** | blocker が 1 件以上あり、直し方が明確 |
| **ESCALATE** | 次のいずれか：2 回修正しても blocker が残る／要件の文言が複数の解釈を許し、どちらかで実装が変わる／修正に仕様の判断が要る／検証を完遂できず、要件の中心が未確認／`onWarning: ask` で判断が要る warning がある |

## 重大度

| 重大度 | 意味 | PR への影響 |
|---|---|---|
| blocker | 実行で証明された問題 | PR を作らない |
| warning | 証明できていない懸念、または証明済みだが止めるほどではない問題 | PR 本文に載せ、レビューに委ねる |
| note | 参考情報、変更前からあった問題 | PR 本文には載せない |

warning のうち次の 4 種類は「判断が要る」として他と分けて載る。`onWarning: ask` のときは、PR の前に確認を求める。

- 自動テストなしの変更（振る舞いは検証時に確かめたが、守る自動テストがない）
- 等価ミュータントの受け入れ提案
- 要件にない変更（害は確認されていない）
- 要件の中心にかかわる未確認

## 段階ごとの基準

検証は 8 段階で進む。段階 1 が落ちたら、そこで打ち切って FIX になる。それ以外は blocker が出ても最後まで進み、指摘をまとめて返す。

### 1. 機械ゲート

プロジェクトの型チェック、lint、テスト、ビルドを実行する。カバレッジのしきい値が設定されていれば、カバレッジつきのテストも実行する。

| 結果 | 重大度 |
|---|---|
| 型チェック、lint、テスト、ビルドのいずれかが失敗 | blocker |
| テストが 1 件も実行されていない | blocker |
| カバレッジのしきい値を割った | blocker |
| 上の失敗が、ベースブランチの時点で既に起きていた | warning |
| その検査がプロジェクトに設定されていない | 未実施として報告（検査を勝手に足さない） |

### 2. ごまかし検出

変更で追加された行だけを機械的に検査する。「完成したように見せる近道」を拾う。

| 検出するもの | 重大度 |
|---|---|
| テストの `.only`（他のテストが実行されなくなる） | blocker |
| テストの `.skip` / `.todo` / `xit` など（何も検証しない） | blocker |
| `@ts-ignore` / `@ts-nocheck` | blocker |
| `debugger` 文 | blocker |
| `@ts-expect-error` | warning |
| `any`、`as unknown as` の二段キャスト | warning |
| lint の無効化コメント | warning |
| 握りつぶした例外（空の `catch`、何もしない `.catch`） | warning |
| スタブ、仮実装、「未実装」の記述 | warning |
| 残ったデバッグ出力（`console.log` など） | warning |
| テストファイルの削除、テストケースの純減 | warning |
| スナップショットの更新 | warning |
| 検査の設定ファイルの変更（lint、型、テスト、CI、mutator の設定） | warning |
| 本番の依存（`dependencies`）の追加 | warning |
| 緩いアサーション（`toBeTruthy` など）、TODO、固定待ち、開発用の依存の追加 | note |

warning と note は 1 件ずつ該当箇所を読んで決める。理由が読み取れれば「確認済み」に移す。ごまかしだと実行で示せたら blocker に上げる（例：握りつぶした例外のせいで、エラー表示が出ないことを再現した）。

カバレッジのしきい値や mutator の重要領域を今回の変更で緩めていたら、要件がそれを求めている場合を除いて blocker。

機械検査で拾えないものとして、**症状だけを隠す修正**も見る。バグ修正で足されたガード、リトライ、既定値へのフォールバックが、起こるはずのない状態を隠していないか。

### 3. 要件適合

要件と変更を突き合わせる。生成時の文脈を持たない別エージェントに任せ、返ってきた指摘は再実行して確かめる。

| 結果 | 重大度 |
|---|---|
| 要件を満たさないことを実行で示せた | blocker |
| 使っている import、API、props、設定キー、パッケージが実在しない | blocker |
| 完了報告の主張が実際と食い違う（「テストを追加」→ 実際は skip、など） | 対応する指摘の重大度。食い違いは専用の節に一覧する |
| 要件にない変更が含まれる（頼まれていないリファクタ、仕様の勝手な拡張） | warning（判断が要る） |
| 実行で確かめられなかった懸念 | warning |
| 要件の文言が複数の解釈を許し、どちらかで実装が変わる | ESCALATE |
| 別エージェントの指摘が再現しなかった | 捨てる（件数と理由を「捨てた指摘」に書く） |

### 4. テストの質

テストが、振る舞いが壊れたときに実際に落ちるかを測る。カバレッジは「実行された」ことしか示さないので、ここではミューテーションテスト（mutator）を使う。コードを 1 か所ずつ小さく書き換え、テストが落ちるかを見る。

| 結果 | 重大度 |
|---|---|
| 新しく足したテストが、何も検出しない | blocker |
| 変更で追加・編集された skip / todo がある | blocker |
| 変更したテストファイルが、テストランナーに拾われていない | blocker |
| 重要領域（プロジェクトが指定）に未検出がある | blocker |
| 変更していないコードの検出力が落ちた（テストを弱めた、消した） | blocker |
| 変更したコードを、どのテストも実行していない | モードによる（下の表） |
| 実行はしているが、書き換えてもテストが落ちない | warning（1 回は修正を試み、残れば PR 本文へ） |
| 変更した関数の中の、今回書き換えていない行の未検出 | 上の扱いから 1 段階下げる |
| 変更したテストが実行するだけの、既存コードの未検出 | note |
| 内部を変えただけで落ちるテスト（実装に張り付いている） | 実際に書き換えて落ちることを示せたら warning |

**変更したコードをどのテストも実行していない場合**

| モード | 条件 | 重大度 |
|---|---|---|
| `strict` | 常に | blocker |
| `standard` | その変更の振る舞いを、実ブラウザ検証や再現テストで確かめた証拠がある | warning（判断が要る：自動テストなしの変更） |
| `standard` | 証拠がない | blocker |

「画面が表示された」は証拠にならない。足した分岐や配置が実際に効いていることを示す確認項目が要る。

全部を blocker にしない理由は 2 つ。どんな入力でも区別できない書き換え（等価ミュータント）が必ず混ざること。実行カバレッジを条件にすると、通すためだけの中身のないテストが増えること。

等価ミュータントの受け入れは、エージェントが自分では行わない。理由つきで提案し、人が決める。エージェントが自分で受け入れられると、すべての穴を「等価です」で通せてしまうため。

mutator が使えない環境では、変更した関数ごとに 1〜2 か所を手動で壊して確かめる。これは網羅ではないので、レポートには「抜き取った N 件はすべて検出された」と書かれ、「テストの質に問題なし」とは書かれない。

型で縛られた値（文字列リテラル型の既定値など）は書き換えると型エラーになり、測られない。その件数はレポートに出る。mutator の数字を「変更は実測済み」の意味で読まないこと。

### 5. 影響範囲

変更が、差分の外で何かを壊していないかを調べる。その変更が安全である根拠を 1 つ特定し、実行で証明する。

見る場所は、検索では出てこない壊れ方が起きるところ。共有コンポーネントや共通フックを使う他の画面、API レスポンスや保存データの形式、実行のタイミング、ライブラリの実際のバージョンでの挙動、機能フラグや環境変数による分岐。

| 結果 | 重大度 |
|---|---|
| 差分の外が壊れることを示せた（同じテストが変更後に失敗し、ベースでは通る） | blocker |
| 安全の根拠を実行で証明できた | 問題なし（証明を載せる） |
| 安全の根拠を証明できなかった | 「未証明」として載せる |

### 6. 実ブラウザ検証

UI に触る変更のときだけ実行する。開発サーバーを起動し、変更した画面を Playwright で操作する。モバイル幅（375px）とデスクトップ幅（1280px）で確かめる。

| 結果 | 重大度 |
|---|---|
| 要件の操作が期待どおりに動かない | blocker |
| 変更によって新たに出たコンソールエラー、未処理例外、失敗したリクエスト | blocker |
| 変更した画面のはみ出し、操作できない要素 | blocker |
| 変更した要素をキーボードで操作できない、axe の critical / serious 違反 | blocker |
| axe の moderate / minor 違反、見た目の軽微な崩れ | warning |
| 現実には起きにくい極端な入力でだけ起きる崩れ | warning |
| 変更前からあった問題 | note |
| 画面に到達できず、要件の中心を確かめられなかった | ESCALATE |
| 画面に到達できず、周辺の項目を確かめられなかった | 「未確認」として PR 本文へ |

既存の E2E テストが通ることは、この段階の代わりにならない。

### 7. フロントエンド観点

変更に関係する項目を選んで確認する。全項目を埋める表ではない。

| 観点 | 見ること |
|---|---|
| 状態の網羅 | ローディング、空、エラー、部分的なデータ、極端な入力、連打と応答の前後、再読み込み |
| アクセシビリティ | キーボード操作、フォーカス、読み上げられる名前、役割に合った要素、状態の通知、色だけに頼らない |
| レスポンシブ | 狭い幅でのはみ出し、固定幅、タッチで押せる大きさ、ホバー頼み |
| フレームワーク特有のミス | effect の依存、不要な effect、`key`、後始末、サーバーとクライアントの境界、ハイドレーション |
| 型の規律 | 外部データを境界でパースしているか、不正な状態を表せない型か、分岐の網羅 |
| デザインの一貫性 | トークンを使わない直書き、既存コンポーネントの再実装、テーマ対応、文言の直書き |
| 差分の最小性 | 要件に対して大きすぎる変更、使われていない引数、既存ユーティリティの再実装、不要な防御 |
| バンドルとパフォーマンス | 追加した依存の大きさ、全体 import、遅延読み込み、画像 |
| セキュリティ | 無害化していない値の HTML 描画、ユーザー入力から作った URL、クライアントに置いた秘密情報 |

ここでも重大度は証拠で決まる。再現手順、コマンド出力、スクリーンショットがあれば blocker、読んで気づいただけなら warning。差分の最小性の指摘は、動作に影響しない限り warning。数字なしに「重くなる」とは書かない。

### 8. 判定とレポート

上の結果から判定を出す。FIX の前には、直し方をコピーの上で試し、それで解消することを確かめる。

修正と再検証は最大 2 回。2 回で直らないものは 3 回目に回さず ESCALATE にする。同じ前提に立った修正が 2 度失敗したなら、間違っているのは修正ではなく前提であり、人が見るべき状況だからである。

## 修正として認めないもの

blocker を消すために次をしても、修正とは扱わない。次の検証で検出される。

- テストを消す、skip する
- lint、型、テスト、カバレッジ、CI の設定を緩める
- `mutator accept` をエージェントが自分で実行する
- モードを `strict` から `standard` に変える

## プロジェクトの基準が優先される

テストをどこまで求めるかは、まずプロジェクト自身が決めた基準に従う。dokumi が独自の線を引くのは、プロジェクトが何も決めていない部分だけ。

| プロジェクトが決めていること | 扱い |
|---|---|
| カバレッジのしきい値 | 段階 1 で検査。割ったら blocker。モードによらない |
| mutator の重要領域としきい値 | 段階 4 で検査。未検出があれば blocker。モードによらない |
| どちらもない | `mode` に従う |

しきい値を満たしていても、今回の変更がテストされているとは限らない（全体で 80% を保ったまま、新しいコードが丸ごと未テストということはあり得る）。そのため、しきい値に合格していても段階 4 は省かれない。

## この基準で確かめられないこと

- **実ブラウザ検証はモックの範囲。** 開発用のモック API で確かめた動作は、実際の API での動作を保証しない。
- **Chromium だけ。** 他のブラウザでの挙動は見ていない。
- **設計の良し悪し。** 動作と証拠は見るが、その設計が妥当かは判断しない。レポートの「人が見るべき箇所」に挙げる。
- **要件そのものの正しさ。** 要件どおりかは見るが、要件が正しいかは見ない。
